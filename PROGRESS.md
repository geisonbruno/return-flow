## Local PostgreSQL host port decision

**Decision:** the ReturnFlow Docker Compose PostgreSQL service defaults to host port **5433** for local development (`infra/docker-compose.yml`, `infra/.env.example`, `apps/api/application-local.properties`, root `CLAUDE.md` §28 all updated together). The container's internal Postgres port is unchanged (`5432`); only the host-side mapping moved, and it remains fully overridable via the existing `POSTGRES_PORT` environment variable.

**Why:** this development machine runs a native Windows PostgreSQL service that was already bound to host port 5432, colliding with Docker's port-forwarding for the same port. Host-network connections to `localhost:5432` could silently land on the native instance instead of the Docker one (different/unknown credentials, connection failures), even though the Docker container itself was always healthy — confirmed in the Phase 1 session and again here. Changing the *project's* default host port sidesteps the conflict without touching the native service (explicitly out of scope — it may be used by other things on this machine) and without hardcoding anything: `POSTGRES_PORT` remains a normal override for any developer whose machine doesn't have this conflict.

**Re-validated 2026-07-26** with no manual override needed (see Chronological history): `docker compose up -d` on the new default, `mvnw spring-boot:run -Dspring-boot.run.profiles=local` connected on the first attempt, `/actuator/health` reported `db: UP` immediately.

## Important architectural decisions

**Phase 0:**

- Spring Boot 4.1.0 + Java 21 (current stable at scaffold time, per start.spring.io metadata).
- `apps/web` scaffolded with the current Vite `react-ts` template, which now ships **oxlint** (not ESLint) and **rolldown-vite** by default. `vite`, `@vitejs/plugin-react`, and `oxlint` were pinned to slightly older minor versions (`vite@6.4.3`, `@vitejs/plugin-react@4.3.4`, `oxlint@1.16.0`) because their latest releases hard-require Node `^20.19.0`, which trips an unrelated npm optional-dependency bug on this machine's Node 20.18.0. `jsdom` pinned to `25.0.1` for the same reason. All can be bumped back to latest once the local/CI Node baseline is >=20.19.
- `apps/mobile` uses the Expo **blank-typescript** template (not tabs/expo-router) to avoid pulling in a navigation library before it's needed.
- MinIO pinned to `RELEASE.2025-09-07T16-13-09Z` (not `:latest`) for reproducibility; Postgres pinned to `16-alpine`.

**Phase 1:**

- **No tenant entity, despite `docs/IMPLEMENTATION_PLAN.md` listing "tenant entity" under Phase 1 deliverables.** The Phase 1 task description given for that session was explicit: "No authentication, tenant logic, users, routes, returns, or business rules should be implemented during this phase," with tenants explicitly out of scope. A direct, detailed instruction for the current phase takes precedence over the higher-level phase description in the implementation plan. The Flyway/JPA/error-handling/OpenAPI/Actuator foundation is ready for the tenant entity to land cleanly at the start of Phase 2.
- **No datasource in the base `application.properties`, by design.** Requiring an explicit `local` or `prod` profile means the app can never silently connect to an undefined or wrong database — it fails fast instead. Trade-off: `mvnw spring-boot:run` requires `-Dspring-boot.run.profiles=local` (documented in both READMEs and `.vscode/tasks.json`).
- **`application-local.properties` hardcodes the same non-secret dev credentials already committed in `infra/.env.example`** (`returnflow`/`returnflow`, env-var overridable) — not a "hardcoded credential" violation since these are throwaway local Postgres credentials already public in the repo. `application-prod.properties` has no defaults at all; it fails to start without `DATABASE_URL`/`DATABASE_USERNAME`/`DATABASE_PASSWORD` from the real deployment environment.
- **PostgreSQL integration-test strategy uses Testcontainers**, not a static test datasource or a manually-started database. `TestcontainersConfiguration` (`@ServiceConnection PostgreSQLContainer`) is imported by any `@SpringBootTest` that needs a real database, so `mvnw test` is self-contained and identical in local dev and CI.
- **springdoc-openapi pinned to `3.0.3`** — the first stable major version compatible with Spring Boot 4.x/OpenAPI 3.1; not managed by Spring Boot's own BOM, so it needs an explicit version.
- **Several Spring Boot 4.1 / Testcontainers 2.0 artifact and package renames were discovered empirically** against real build failures, not guessed:
  - Flyway now requires the dedicated `spring-boot-starter-flyway` starter plus `flyway-database-postgresql` for Postgres support.
  - Testcontainers 2.0 renamed its modules with a `testcontainers-` prefix (`org.testcontainers:testcontainers-junit-jupiter`, `org.testcontainers:testcontainers-postgresql`).
  - `@WebMvcTest`/`@AutoConfigureMockMvc` moved to `org.springframework.boot.webmvc.test.autoconfigure`.
  - `SpringPhysicalNamingStrategy` was removed entirely in Boot 4; Hibernate's own default naming strategy already produces this project's `snake_case` convention, so nothing was lost by not setting it.
  - `HibernateJpaConfiguration` and friends now live under `org.springframework.boot.hibernate.autoconfigure`.

**Finalization (2026-07-26):** the local PostgreSQL host port decision above is the only architectural change made while closing out Phases 0–1; no new product functionality or capability was introduced, per that task's explicit scope.

**Phase 2A:**

- **`TenantContext` is a static `ThreadLocal` holder, modeled directly on Spring Security's `SecurityContextHolder`.** It's the same well-established pattern for propagating request-scoped identity without threading a parameter through every call site; callers only ever see `set`/`get`/`clear`, never the storage mechanism, per this phase's explicit requirement.
- **`TenantContext` stores the resolved `Tenant` entity itself, not just its ID.** Simplest option for now (matches the literal "store current tenant" wording and avoids a repository round-trip everywhere the current tenant is needed); worth revisiting if a lighter identifier-only context is needed once real tenant-scoped queries start using it in Phase 3+.
- **`TenantFilter` is registered explicitly via a `FilterRegistrationBean`, not `@Component`.** A plain component-scanned `Filter` bean is auto-included by `@WebMvcTest` slices anywhere in the app (Spring Boot's web-slice inclusion matches on bean *type*, `Filter`, regardless of which package declares it) — this broke Phase 1's existing `GlobalExceptionHandlerTest` slice, which has no database configured, once `TenantFilter`'s `TenantResolver → TenantRepository` dependency chain got pulled in. Wrapping registration in a `FilterRegistrationBean` (declared in `TenantFilterConfig`, not a `Filter`-typed bean itself) keeps `TenantFilter` out of unrelated web slices while still applying to every real request. Found and fixed against an actual failing `mvnw test` run, not guessed.
- **Bootstrap idempotency is a simple check-then-create (`existsBySlug` then `save`), not a transactional upsert or explicit concurrency guard.** The unique constraint on `tenant.slug` (`uk_tenant_slug`) is the actual correctness guarantee against duplicates; the check is just an optimization to avoid a constraint-violation exception on the common path. This is intentionally not hardened further for concurrent multi-instance startup, which doesn't exist for this single-instance pilot — revisit if/when the API ever runs with more than one replica.
- **No "tenant isolation" tests in this phase**, despite `docs/IMPLEMENTATION_PLAN.md` listing it as a Phase 2A deliverable. There is exactly one tenant and no tenant-scoped business data yet (no user/route/return tables), so there is nothing to isolate from anything else — a test asserting isolation today would only be able to assert against itself. Real isolation tests belong with the first tenant-owned business entities (Phase 2B/2C onward), where a second tenant and cross-tenant access attempt can be meaningfully constructed. Same "explicit phase instructions narrow the plan doc" precedent as Phase 1's tenant-entity deviation.
- **Every request resolves the tenant via a database lookup (`findBySlug`) with no caching.** Matches "current implementation always resolves the default Warehouse tenant" literally; acceptable for a single-tenant pilot. Caching or a cheaper resolution path is a reasonable, deliberately deferred optimization once `TenantResolver` grows real per-request resolution logic (JWT/headers) in a later phase.
- **`Auditable` (`createdAt`/`updatedAt` via Spring Data JPA auditing, `@MappedSuperclass` + `@EnableJpaAuditing`) is the first entry in `common/`'s base-entity conventions**, established here specifically because this phase asked for it ahead of the first real entity (`Tenant`). No `createdBy`/`updatedBy` — no authenticated user exists yet to attribute them to.

**Phase 2B:**

- **Phase 2A's `TenantFilter`/`TenantFilterConfig` are deleted, not kept alongside the new mechanism.** Their entire purpose — resolving a hardcoded default tenant for *every* request, authenticated or not — became obsolete the moment real authentication existed (root `CLAUDE.md` §21.1 always described that resolver as temporary, tenant-foundation-phase-only). Keeping both running would have been exactly the "two competing tenant-resolution mechanisms" the phase brief explicitly warned against, and it would have populated `TenantContext` for public/unauthenticated requests (health checks, failed logins) for no reason. `TenantResolver` changed from a no-arg `resolve()` to `resolve(UUID tenantId)` (looks up by ID, requires `ACTIVE`, throws `TenantNotActiveException` otherwise); `DefaultTenantResolver` keeps its name as the sole implementation. The only caller is the new `auth.security.JwtAuthenticationFilter`, added to the Spring Security filter chain via `addFilterBefore(..., UsernamePasswordAuthenticationFilter.class)` — i.e. tenant resolution now happens *inside* the security chain, immediately after a bearer token validates, rather than as an independent servlet filter outside it. This is the "refactor into the appropriate Spring Security integration" the phase brief anticipated as a possible outcome; it was necessary because tenant resolution now inherently depends on an authenticated identity that only the security chain can provide. `TenantContext` is still cleared in a `finally` block exactly as before (Phase 2A's pattern), and `SecurityContextHolder` clearing is handled automatically by Spring Security's own `SecurityContextHolderFilter` under `SessionCreationPolicy.STATELESS` — no manual clearing needed there.
- **Refresh tokens are hashed with SHA-256 (`java.security.MessageDigest`), not BCrypt.** The raw value is already a 256-bit `SecureRandom` opaque token, not a low-entropy human password, so it needs no per-row salt or deliberately-slow KDF to resist guessing — and a deterministic digest is what makes an O(1) unique-index lookup by hash possible at all (BCrypt's per-hash salt makes indexed lookup-by-hash impossible). Same pattern GitHub/GitLab use for PATs/session tokens. `MessageDigest` is a standard JDK primitive, not hand-rolled crypto — BCrypt (via Spring Security's `BCryptPasswordEncoder`) is still used for actual user passwords.
- **Two significant Spring Boot 4.1 / Spring Security 7.1 discoveries, found empirically against real build/runtime failures (same precedent as Phase 1's artifact renames):**
  - Boot 4.1 auto-configures a **Jackson 3** (`tools.jackson.databind.ObjectMapper`, groupId `tools.jackson.core`) bean, not classic Jackson 2 (`com.fasterxml.jackson.databind.ObjectMapper`) — the latter is only incidentally on the compile classpath (pulled in transitively by `springdoc-openapi`/`jjwt-jackson`) but has **no Spring-managed bean**. Anything that needs an injected `ObjectMapper` (the two custom Spring Security `AuthenticationEntryPoint`/`AccessDeniedHandler` beans, and JSON handling in `AuthControllerIntegrationTest`) must import `tools.jackson.databind.*`, not `com.fasterxml.jackson.databind.*`.
  - Security auto-configuration classes moved out of `spring-boot-autoconfigure` entirely into a new `spring-boot-security` artifact, under `org.springframework.boot.security.autoconfigure.*` (not the Boot-3-era `org.springframework.boot.autoconfigure.security.servlet.*`, which no longer exists). `GlobalExceptionHandlerTest`'s `@WebMvcTest` slice needed `excludeAutoConfiguration` on `SecurityAutoConfiguration`, `SecurityFilterAutoConfiguration`, and `ServletWebSecurityAutoConfiguration` (all three, from the new package) to stop Spring Security's classpath-triggered deny-by-default behavior from turning that test's expected 400/500 responses into 401s — that test is about generic error handling, unrelated to auth, and never loads the real `auth.security.SecurityConfig` bean (a `@WebMvcTest` slice only loads `@Controller`/`@RestControllerAdvice` beans plus auto-configuration).
- **`UserDetailsServiceAutoConfiguration` is explicitly excluded on `@SpringBootApplication`.** This API never uses Spring Security's `UserDetailsService`/`AuthenticationManager` model — authentication is entirely bearer-token-based via `JwtAuthenticationFilter`. Left enabled, Boot registers an inert in-memory user with a random password logged at every startup; excluding it removes meaningless noise, not a real capability.
- **Login, refresh, and `/me` each use one single generic exception per endpoint** (`InvalidCredentialsException`, `InvalidRefreshTokenException`, `InactiveUserException` respectively) covering every distinct failure cause for that endpoint (unknown email / wrong password / inactive account all produce the identical login error, for instance) — deliberate, per the phase's explicit no-account-enumeration requirement, proven by an integration test asserting the wrong-password and unknown-email responses are byte-identical.
- **`AccessTokenService` takes an injected `java.time.Clock`, used only when issuing a token** (to compute `iat`/`exp`) — `validate()` needs no clock override, since JJWT always checks the embedded absolute `exp` claim against real wall-clock time regardless of what clock issued the token. This is what makes "expired token fails" deterministically unit-testable (issue with a `Clock` fixed in the past) without `Thread.sleep`. A single `Clock.systemUTC()` bean (`config.ClockConfig`) is shared by `AccessTokenService` and `RefreshTokenService`.
- **`TenantDefaults` (Phase 2A, previously package-private) is widened to `public`.** `user.UserBootstrap` needs the Warehouse slug constant to assign its bootstrapped admin to the right tenant, and reusing the existing constant (rather than a duplicated magic string) matches that class's own original javadoc intent.
- **`TenantBootstrap` and `UserBootstrap` are ordered explicitly (`@Order(1)`/`@Order(2)`)** — `ApplicationRunner`s otherwise execute in unspecified order, and the admin bootstrap requires the Warehouse tenant to already exist.
- **JWT library is `io.jsonwebtoken:jjwt` (0.12.6, api/impl/jackson), HS256.** A small, focused, actively-maintained library rather than pulling in the heavier OAuth2-resource-server machinery for what is a purely self-issued, single-service token — no external identity provider or token-introspection endpoint exists or is planned.
- **One deliberate test-coverage boundary**: no protected endpoint re-checks a user's active status against the database on every single request — only `/auth/me` does, per its explicit requirement. Re-checking on every request would negate the point of a short-lived stateless access token (currently 15 minutes); an inactive user's existing token simply expires naturally within that window, same as any other claim in it.

**Phase 2B review fixes:**

- **Login timing side-channel closed via a pre-initialized dummy BCrypt hash, not per-request encoding or sleeps.** `AuthenticationService` now computes one dummy hash once in its constructor (a singleton bean, so this runs once at startup) and always calls `passwordEncoder.matches` — against the real hash if the email resolves to a user, against the dummy hash otherwise — before evaluating existence, active status, or password correctness. This makes the unknown-email and inactive-user failure paths pay the same BCrypt cost as a wrong-password attempt on a real active user, closing a response-time distinguisher that previously let an attacker enumerate valid emails even though every path already returned an identical response body. Proven by a dedicated test using a hand-written recording `PasswordEncoder` wrapper (not a mocking framework — this codebase's established convention) that counts `matches` invocations, deliberately avoiding flaky wall-clock timing assertions.
- **`AccessTokenService.validate()` now explicitly null-checks the mandatory claims (`sub`, `tenantId`, `role`) before parsing them**, rather than relying on catching `IllegalArgumentException`/`JwtException` alone. A validly-HS256-signed token missing a claim previously threw an uncaught `NullPointerException` (`UUID.fromString(null)`/`Enum.valueOf(null)` both throw NPE, not `IllegalArgumentException`) that neither `validate()` nor `JwtAuthenticationFilter` caught, surfacing as a raw 500 instead of a clean 401. The fix adds an explicit presence check and returns `Optional.empty()` — no broad `catch (RuntimeException ...)` was introduced, per the review's explicit instruction. Proven at both the unit level (`AccessTokenServiceTest`, hand-crafting validly-signed tokens with missing/malformed/invalid claims via JJWT directly) and the full HTTP level (`AuthControllerIntegrationTest.meWithAValidlySignedTokenMissingAMandatoryClaimIsUnauthorizedNotAServerError`).
- **The security-chain-level 401 (`RestAuthenticationEntryPoint`) is now body- and content-type-asserted**, not just status-code-asserted, for both a missing token and a tampered one. The access-denied path (`RestAccessDeniedHandler`) is unit-tested directly with Spring's real `MockHttpServletRequest`/`MockHttpServletResponse` test doubles (not a mocking framework, and not a real HTTP round-trip) rather than fabricating a Phase 2C role-restricted endpoint just to exercise a genuine 403 — there is still no authorization-restricted path in the product at this phase.
- **Migrations `V3`/`V4` were explicitly left unmodified** per the review's own classification of the unnamed foreign-key constraints as cosmetic/non-blocking; that naming convention is deferred to future migrations rather than editing already-drafted ones for a non-functional rename.
