- **Repository governance and CI**: `main` is the default branch; all work happens on a `feat`/`fix`/`chore`/`docs` branch and reaches `main` only through a Pull Request (see `docs/DEVELOPMENT_WORKFLOW.md`). New (Phase 10A, approved): **three independent workflows instead of one combined `ci.yml`** — `backend.yml` (**Backend CI**: `mvnw package`, which runs the full test suite before packaging), `web.yml` (**Web CI**: `npm ci`, lint, typecheck, tests, production build), and `mobile.yml` (**Mobile CI**: `npm ci`, typecheck, lint, `npm test -- --ci --runInBand`; no Expo Doctor step), each of which starts for every Pull Request to `main` — so `Backend CI`, `Web CI`, and `Mobile CI` always report and can safely be required — but runs its expensive setup and validation only when that application's own paths (or its own workflow file) actually changed, detected from a native `git diff` of the Pull Request's base and head SHAs rather than a third-party action. ## Architectural decisions

**Stack and tooling:**

- Spring Boot 4.1.0 + Java 21; `springdoc-openapi` pinned to `3.0.3` (first version compatible with Boot 4.x/OpenAPI 3.1, not managed by Boot's own BOM).
- `apps/web` pins `vite@6.4.3`/`@vitejs/plugin-react@4.3.4`/`oxlint@1.16.0`/`jsdom@25.0.1` because newer releases require Node `>=20.19`, above this machine's Node `20.18.0`; bump once the local/CI Node baseline moves.
- `apps/mobile` started from Expo's `blank-typescript` template; Phase 4 added `@react-navigation/native`/`native-stack`, `react-native-screens`, `react-native-safe-area-context`, and `expo-secure-store` once actually needed (see Phase 4 decisions below).
- MinIO pinned to `RELEASE.2025-09-07T16-13-09Z`, Postgres to `16-alpine`, for reproducibility.
- No datasource is configured in base `application.properties` — an explicit `local` or `prod` profile is always required, so the app never silently connects to an undefined database.
- Testcontainers (not a static test datasource) backs every integration test that needs a real database, so `mvnw test` is self-contained and identical in local dev and CI.

**Multi-tenancy and authentication:**

- `TenantContext` (a static `ThreadLocal`, modeled on `SecurityContextHolder`) is populated exclusively from the authenticated principal, by `auth.security.JwtAuthenticationFilter` inside the Spring Security filter chain. `TenantResolver.resolve(UUID)` looks the tenant up by ID and requires `ACTIVE` status; `DefaultTenantResolver` is the only implementation.
- Refresh tokens are 256-bit `SecureRandom` opaque values, persisted only as SHA-256 hashes (not BCrypt — the raw value is already high-entropy, and a deterministic digest is what makes O(1) hash lookup possible for rotation/revocation). User passwords use BCrypt via Spring Security's `BCryptPasswordEncoder`.
- Login always performs the password comparison — against a pre-initialized dummy BCrypt hash when the email doesn't resolve to a user — before evaluating existence, active status, or password match, so no failure path is faster than another (prevents email enumeration via response timing).
- `AccessTokenService.validate()` explicitly null-checks the mandatory claims (`sub`, `tenantId`, `role`) before parsing them, so a validly-signed token missing a claim fails validation cleanly instead of throwing.
- Login, refresh, and `/me` each raise one exception type covering every failure cause for that endpoint, so responses never reveal which specific condition failed.
- JWT library is `io.jsonwebtoken:jjwt` (HS256) — small and sufficient for a self-issued, single-service token; no OAuth2/external identity provider is planned.
- No protected endpoint re-checks user active-status on every request except `/auth/me` (its explicit requirement) — re-checking everywhere would defeat the purpose of a short-lived (15-minute) stateless access token.
- `UserDetailsServiceAutoConfiguration` is excluded — this API never uses Spring Security's `UserDetailsService`/`AuthenticationManager` model, only bearer-token auth via `JwtAuthenticationFilter`.
- `ApplicationRunner` bootstraps (`TenantBootstrap`, `UserBootstrap`) are ordered explicitly (`@Order(1)`/`@Order(2)`, tenant before admin) and both use the same check-then-create idempotency pattern, backed by a database unique constraint as the actual correctness guarantee.

**Framework specifics for this exact stack (Spring Boot 4.1 / Spring Security 7.1)** — worth knowing before touching security or JSON code again:

- Security auto-configuration lives under `org.springframework.boot.security.autoconfigure.*` (not the Boot-3-era `org.springframework.boot.autoconfigure.security.servlet.*`).
- The auto-configured `ObjectMapper` bean is **Jackson 3** (`tools.jackson.databind.ObjectMapper`), not classic Jackson 2 (`com.fasterxml.jackson.databind.ObjectMapper`, which is only incidentally on the classpath via `springdoc`/`jjwt-jackson`). Anything needing an injected `ObjectMapper` must import the `tools.jackson` package.
- **`@ControllerAdvice`/`@RestControllerAdvice` beans need an explicit `@Order`, or a more specific handler can be silently shadowed by a less specific one.** Spring picks the first advice bean (by order, defaulting to `Ordered.LOWEST_PRECEDENCE` — i.e. unordered beans tie with each other, not with anything "later") that has *any* matching `@ExceptionHandler` for the thrown type; it does not compare specificity across beans. `GlobalExceptionHandler`'s blanket `Exception.class` fallback was accidentally "safe" only because `AuthExceptionHandler` happened to sort alphabetically before it — adding `route.RouteAdminExceptionHandler`/`user.UserAdminExceptionHandler` in this phase broke that luck immediately (every one of their intended 400/404/409 responses came back as 500, caught by a real failing `mvnw test` run). Fixed by giving every feature-specific advice `@Order(Ordered.HIGHEST_PRECEDENCE)` and `GlobalExceptionHandler` `@Order(Ordered.LOWEST_PRECEDENCE)` (documents intent; the real guarantee comes from the feature-specific side). Any future `@RestControllerAdvice` must follow the same pattern.

**Route and user administration (Phase 2C):**

- `route.Route` and its admin endpoints follow the same shape as `user`'s Phase 2B conventions: a normalization utility (`RouteCodeNormalizer` — trim + uppercase, mirroring `EmailNormalizer`), tenant-scoped repository lookups (`findByIdAndTenantId`) so a cross-tenant ID behaves as not found, and a dedicated `@RestControllerAdvice` per feature module.
- Route codes are unique per `(tenant_id, code)`, not globally — the same code is expected to recur across different tenants (e.g. every tenant might have a "1").
- `/api/v1/admin/**` authorization is a single `hasRole("ADMIN")` URL-pattern rule in `SecurityConfig`, not method-level annotations — `JwtAuthenticationFilter` already grants `ROLE_<role>` from the validated token, so no new wiring was needed beyond the one rule.
- The DRIVER/ADMIN ↔ route invariant is enforced once, in `UserAdminService.validateRouteAssignment`, used identically by create (always `resultingActive=true`, since created users are always active) and update (`resultingActive=request.active()`): ADMIN must have no route; an active DRIVER must have an active, same-tenant route; an *inactive* DRIVER may be left without one. A route can't be deactivated while any active DRIVER still references it (`UserRepository.existsByRouteIdAndActiveTrueAndRole`).
- Self-protection (an admin can't deactivate or demote themselves) is a plain equality check against the authenticated principal's own user ID in `UserAdminService.update`, not a permission-framework feature — deliberately simple, per this phase's explicit "no complex permission hierarchy" boundary.
- Password reset revokes every existing refresh-token session for that user (`RefreshTokenService.revokeAllForUser`, a new bulk operation) but leaves any still-valid access token alone, consistent with the existing Phase 2B decision not to re-check active-status per request — the user's *next* refresh attempt (not their current access token) is where a reset actually takes effect.
- `User`/`Route` gained explicit full-replace `update(...)` mutators (matching PUT semantics) — Phase 2B's `User` had none, since no admin CRUD existed yet; both remain otherwise immutable outside their own module.
- The `/admin/users` response DTO field is `name` (matching this phase's explicit request/response spec), while `/auth/me` (Phase 2B) already shipped as `fullName` — a deliberate, minor inconsistency left as-is rather than retroactively renaming an already-approved contract; both map to the same `User.fullName` internally. Worth knowing before building a web client against both.
- `UpdateRouteRequest.active`/`UpdateUserRequest.active` are `@NotNull Boolean`, not primitive `boolean` — found in review: a primitive silently deserializes a missing JSON field to `false`, which would have let an incomplete PUT body deactivate a route or user by accident. The service layer unboxes to a local primitive once, immediately after `@Valid` has already guaranteed non-null, and uses that everywhere else.

**Return domain model (Phase 3A):**

- `returnrecord.ReturnRecord` is the first entity in this codebase to use genuine `@ManyToOne(fetch = LAZY)` JPA associations (to `Tenant`, `User` as driver, `Route`) instead of raw `tenantId`-style UUID columns — a deliberate, explicitly-requested exception to the convention every other entity follows, justified by this being the first entity that references three different aggregate roots at once. The relationships stay strictly unidirectional: none of `Tenant`/`User`/`Route` gained a back-reference collection, and nothing cascades to them. Spring Data's property-path resolution still derives `findByIdAndTenantId(id, tenantId)` correctly against the `tenant` association (resolving to `tenant.id`) with no extra configuration.
- `ReturnRecord.route` is a snapshot of the driver's route **at creation time**, not a live derivation — set once by `ReturnRecordCreator` and never updated afterward, so a later route reassignment never rewrites an existing return's history. Only a direct `route_id` foreign key is stored; no route-code/name snapshot columns were added, since nothing in the current source-of-truth documents requires displaying a route's historical code/name independent of the live `Route` row.
- Return numbers (`RF-000001`, ...) come from one global PostgreSQL sequence (`return_number_seq`), read via a plain native `SELECT nextval(...)` through `EntityManager` — not row counts, timestamps, or in-memory counters, all unsafe under concurrent creation. `String.format("RF-%06d", ...)` zero-pads to a minimum of six digits without ever truncating, so formatting keeps working correctly past `RF-999999` by simply growing wider. One global (not per-tenant) sequence is an intentional MVP simplicity trade-off for the single-company pilot, consistent with this phase's explicit scope.
- `ReturnRecordCreator` is the single place every return-creation rule lives (role/active/route/tenant validation, customer-name/observation normalization, number generation, initial status) specifically so the future driver API (Phase 3B) never has to reimplement them — it takes the caller's already-authenticated `Tenant`/`User` directly and never reads `TenantContext` itself, keeping the domain layer free of any assumption about how the caller authenticated.
- `ReturnRecord`'s constructor is package-private, callable only from `ReturnRecordCreator` (same package) — an additional safeguard beyond what was strictly asked, ensuring no code outside the `returnrecord` package can construct a return while bypassing its validation rules.
- No HTTP exception handler was added for the new domain exceptions (`DriverRequiredException`, `InactiveRouteException`, etc.) — this phase has no controller; Phase 3B maps them to `ProblemDetail` responses when the driver API exists to receive them.
- Testing return-number generation against the exact starting value (`RF-000001`) needs a genuinely pristine `return_number_seq`, which the suite's normal shared/cached Testcontainers context can't guarantee (many test classes reuse one cached container). `ReturnNumberGeneratorFreshDatabaseTest` isolates that one assertion with `@DirtiesContext(classMode = BEFORE_CLASS)`, forcing a fresh context+container before it runs; every other return-number test asserts only relative behavior (increments, uniqueness, format) so it's safe to run in any order against the shared context.
- `ReturnRecordCreator.create()` explicitly rejects a `null` `reason` (`InvalidReasonException`) before any route/route lookup, normalization, number generation, or persistence — found in review: without this guard, a null reason relied entirely on the database's `NOT NULL` constraint as the only backstop, which prevented bad data but leaked a raw persistence exception instead of a clean domain one, inconsistent with every other invalid-input path. Proven by a test that confirms both no row is persisted and no return number is consumed by the rejected attempt (via a before/after relative comparison, not an absolute sequence value).

**Driver return API and return model corrections (Phase 3B):**

- **Return reason contract reconciled with root CLAUDE.md (resolves the discrepancy noted during initial implementation):** `ReturnReason` now uses the exact 11 codes from CLAUDE.md §10 (`WRONG_ITEM_DELIVERED`, `EXTRA_ITEM`, `MISSING_ITEM`, `CUSTOMER_CHARGE_REQUIRED`, `NO_LONGER_REQUIRED`, `WRONG_ITEM_ORDERED`, `EXCHANGE_REQUIRED`, `DAMAGED`, `LEAKING`, `NOT_ORDERED`, `OTHER`), replacing the differently-spelled temporary Phase 3B names outright — no compatibility aliases, since no client has shipped against the temporary names. The conditional free-text field is likewise renamed to `reasonDetails` (Java field/getter, `NewReturn` record component, DTO property, exception class `InvalidReasonDetailsException`), matching CLAUDE.md §10.1. The V8 migration's physical column, `other_reason_details`, was **not** renamed (out of scope for this correction, and V8 was explicitly not to be touched) — `ReturnRecord.reasonDetails` maps to it explicitly via `@Column(name = "other_reason_details")`, a deliberate, commented Java/DB name mismatch. No new migration was added.
- `ReturnRecordCreator.create(...)` takes a package-private nested record, `NewReturn` (customerName, reason, reasonDetails, quantity, unit, observation), instead of growing to an 8-parameter method — deliberately not the HTTP request DTO itself, so the domain service stays decoupled from any particular API contract, and deliberately not named `Command` to avoid suggesting a CQRS/command-bus pattern this codebase explicitly avoids. Follows the same nested-record convention already used by `AccessTokenService.IssuedAccessToken`/`RefreshTokenService.IssuedRefreshToken`.
- `quantity`/`unit`/`reasonDetails` are validated inside `ReturnRecordCreator`, not only via Bean Validation on the request DTO — mirrors the existing `reason` null-check precedent (Phase 3A review fix) and keeps the domain service safe for any future caller that doesn't go through this DTO. `reasonDetails` is rejected (not silently nulled) when supplied for a non-`OTHER` reason, keeping the API contract unambiguous about which field actually drove the return.
- V8 (`V8__add_return_quantity_unit_and_other_reason.sql`, unmodified by the reason-contract correction, later targeted-fixed for the unit code — see below) adds `quantity NOT NULL`/`unit NOT NULL` with a temporary `DEFAULT` immediately dropped after the `ALTER TABLE`, rather than assuming the table is empty — safe regardless of whether `return_record` already has rows (it does not, as of this migration: Phase 3A shipped no endpoint capable of persisting a real row outside ephemeral Testcontainers runs, but a migration should not depend on that remaining true). `other_reason_details` stays nullable at the database level; its conditional requirement is application-only. Two named `CHECK` constraints (`chk_return_record_quantity_positive`, `chk_return_record_unit_valid`) enforce `quantity > 0` and `unit IN ('CTN','EA')` at the database layer as a backstop beneath the domain validation. V1–V8 were not modified by either correction (both were targeted fixes to files not yet committed).
- `DriverReturnService.list`/`.get` are `@Transactional(readOnly = true)` — the first read methods in this codebase that need it. `ReturnRecord.driver`/`.route` are `fetch = LAZY`; under this project's `spring.jpa.open-in-view=false`, a read method with no open transaction would throw `LazyInitializationException` the moment DTO mapping touches `returnRecord.getDriver().getFullName()` after the originating repository call's own short transaction has already closed. Phase 2C's `route`/`user` read methods never needed this because those entities store raw UUID columns, not JPA associations — this is a new, `return_record`-specific concern, not a change to prior conventions.
- The authenticated driver's tenant/route are always internally consistent by construction (the driver row is looked up via `userRepository.findByIdAndTenantId(principal.userId(), tenant.getId())`, and a driver's route was already tenant-validated at assignment time by Phase 2C), so `ReturnRecordCreator`'s `DriverTenantMismatchException`/`RouteTenantMismatchException` are unreachable through the driver endpoints today — they stay mapped in `DriverReturnExceptionHandler` purely as defense-in-depth for any future caller of `ReturnRecordCreator`, consistent with Phase 3A's own reasoning for keeping them.
- `/api/v1/driver/**` is one additional `hasRole("DRIVER")` URL-pattern rule in `SecurityConfig`, alongside the existing `/api/v1/admin/**` → `hasRole("ADMIN")` rule — no new wiring needed, same as Phase 2C's admin rule.
- **Return unit code corrected to match root CLAUDE.md (found during final Phase 3B review):** `ReturnUnit` used a temporary `CT` value for the carton unit; root `CLAUDE.md` §11.2/§11.3/§16.3/§31.3/§40, `apps/api/CLAUDE.md`, and `docs/IMPLEMENTATION_PLAN.md` all unanimously specify `CTN` (Carton), alongside `EA` (Each) — CLAUDE.md §40 lists this as an already-decided V1 value. `CT` was removed outright (no alias, no deprecated value, no automatic conversion) and replaced with `CTN` in the enum, V8's `chk_return_record_unit_valid` constraint, and every test. `EA` was unaffected.

**Mobile driver workflow (Phase 4):**

- **Deliberately narrows `docs/IMPLEMENTATION_PLAN.md`'s Phase 4 section, not a silent contradiction (confirmed correct on final review):** that document's Phase 4 deliverables/acceptance criteria additionally list editing while `WAITING_WAREHOUSE`, a customer representative name, automatic refresh-to-read-only when warehouse review starts, and dynamically loading active reasons from a backend reason endpoint. This implementation deliberately deferred all four, because the approved backend does not yet support them or they belong to a later phase: no edit/status-transition endpoint exists in the approved Phase 3B backend; customer representative name belongs with the signature-collection work root CLAUDE.md §13 describes for Phase 5; and no `GET /api/v1/reasons` endpoint exists, so the mobile app uses the approved canonical `ReturnReason` values hardcoded locally (`returns/returnOptions.ts`) instead of fetching them. The developer should reconcile `docs/IMPLEMENTATION_PLAN.md`'s Phase 4 section with this narrower, backend-feasible slice, or explicitly schedule the deferred items into a later phase.
- Tokens live only in Expo SecureStore (`auth/tokenStorage.ts`) — never AsyncStorage, never a plain module variable as the only copy. `api/apiClient.ts` keeps an in-memory copy for request signing, but every write to that in-memory copy (login, background-refresh rotation, logout) has a matching SecureStore write/clear, so app restart always resumes from the same state a background rotation would have produced.
- `api/apiClient.ts`'s 401-retry is a single shared module, not per-screen logic: on a 401, exactly one refresh is attempted (concurrent 401s from unrelated screens share one in-flight refresh promise, not one each), the original request retries exactly once with the rotated token, and a still-failing retry (or a failed refresh itself) clears the session and fires a registered `onSessionExpired` callback that `AuthContext` uses to route back to Login — this covers a background 401 triggered deep inside any screen's API call, not only an explicit login/logout action.
- `EXPO_PUBLIC_API_BASE_URL` is read lazily and memoized by `config/environment.ts`, not eagerly at module import — it throws a clear, actionable error only when actually needed (first API call), rather than crashing every test file that happens to import something in the dependency chain. `.env.example`'s default is an explicit `YOUR_COMPUTER_LAN_IP` placeholder, not a real address, since a physical phone cannot reach the laptop via `localhost`.
- One `@react-navigation/native-stack` navigator whose available screens depend entirely on `AuthContext`'s `status` (`loading` / `unauthenticated` / `authenticated`) — the officially recommended React Navigation pattern for gating an authenticated flow, rather than a second navigator or a manual visibility toggle. `ReturnDetails` receives only `{ returnId: string }` as a navigation param, never the full `ReturnRecord`, so the screen always re-fetches the authoritative current state instead of trusting whatever was true when the list rendered.
- `CreateReturnScreen` navigates to `ReturnDetails` with `navigation.replace(...)`, not `navigate(...)`, after a successful submission — the just-submitted form is removed from the stack entirely, so back-navigation from the created return's details goes to My Returns, not back into a pointless, already-submitted create form (this phase has no edit capability, so re-entering the form after creation would only confuse).
- Client-side `returns/returnValidation.ts` mirrors the backend's exact limits (`CUSTOMER_NAME_MAX_LENGTH = 200`, `OBSERVATION_MAX_LENGTH = 2000`, `REASON_DETAILS_MAX_LENGTH = 500`) and rules (quantity: positive whole number only; `reasonDetails` required only for `OTHER` and never included in the built payload otherwise) purely for immediate UX feedback — the backend remains the sole authority and re-validates independently, per root CLAUDE.md's "validate input on client and server" principle.
- `returns/returnOptions.ts`'s reason/unit/status label maps are typed `Record<ReturnReason, string>` / `Record<ReturnUnit, string>` / `Record<ReturnStatus, string>` rather than partial maps with a runtime fallback — adding a new backend enum value without updating the mobile label map is a TypeScript compile error, not a silently-blank or wrong label shown to a driver.
- No state-management library (Redux/Zustand/MobX/React Query), no Axios, no form library was added — React Context (`AuthContext`) for session state, plain `useState`/native `fetch` everywhere else, per the phase's explicit "keep it simple" instruction. The only new runtime dependencies are `@react-navigation/native`, `@react-navigation/native-stack`, `react-native-screens`, `react-native-safe-area-context`, and `expo-secure-store` — installed via `expo install` at the exact versions it resolved as compatible with the already-pinned Expo SDK 57.x.

**Local web testing support (post-Phase-4 patch):**

- Expo SecureStore has no browser implementation, so `npx expo start --web` alone left the app stuck on session restoration (`ExpoSecureStore.default.getValueWithKeyAsync is not a function`). Fixed with `auth/tokenStorage.web.ts`, a browser-`localStorage`-backed implementation of the exact same `saveTokens`/`loadTokens`/`clearTokens` API as `auth/tokenStorage.ts` — React Native Web's platform file resolution (Metro prefers `*.web.ts` over the extensionless file when bundling for `web`) swaps it in automatically; no changes were needed to `AuthContext.tsx` or `apiClient.ts`, since both already import `tokenStorage` via its extensionless path. Verified by inspecting the compiled web bundle directly: zero references to `expo-secure-store`/`getValueWithKeyAsync` (the module isn't even included for web), and the `localStorage`-based implementation present and reachable.
- **Native token persistence is unchanged and remains Expo SecureStore** — `tokenStorage.ts` only had its `StoredTokens` type relocated to the shared `auth/types.ts` (to avoid declaring it twice across the two platform files); its SecureStore-backed logic was not touched.
- The web adapter is explicitly a development/testing convenience, not a production browser-security decision: it clears a partial (only-one-token-present) session, treats any `localStorage` access failure as "no session" rather than crashing, and never lets a token value reach a thrown error — but `localStorage` itself offers none of SecureStore's platform-level protections, so it must not be presented as equivalent.
- `react-dom` and `react-native-web` were added (matching the pinned `react`/Expo SDK 57 versions) purely to make `expo start --web` possible; no other web-specific dependency was introduced.

**Local-profile CORS (post-Phase-4 patch):**

- Expo Web (`http://localhost:8081`) and the API (`http://localhost:8080`) are different browser origins, so the browser blocked every request with a CORS preflight failure once the SecureStore/web-storage fix let the app actually reach the Login screen. Fixed with a `UrlBasedCorsConfigurationSource` bean in `auth.security.SecurityConfig`, allowing exactly the origin in `app.cors.local-origin` (`application-local.properties`, `http://localhost:8081`) for `GET`/`POST`/`OPTIONS` with `Authorization`/`Content-Type`/`Accept` headers, scoped to `/api/v1/**`. `allowCredentials` stays `false` — auth is bearer-token based, never browser cookies.
- **The bean is annotated `@Profile("local")`, so it — and the CORS allowance entirely — does not exist in any other profile**; production and any other profile behave exactly as before this patch. Proven by a dedicated test running with no active profile (this project's normal default) asserting the same origin string gets no `Access-Control-Allow-Origin` header.
- The `securityFilterChain(...)` bean now takes `Optional<UrlBasedCorsConfigurationSource>` (the concrete type, not the broader `CorsConfigurationSource` interface) and only calls `.cors(...)` when present — deliberately narrow, because Spring MVC's own auto-configured `mvcHandlerMappingIntrospector` bean *also* implements `CorsConfigurationSource`, so injecting the interface type resolves ambiguously (two candidate beans) the moment any profile registers this bean; the concrete type only ever matches this one.
- No other security rule changed: `.authorizeHttpRequests(...)` is untouched, so every existing authentication/role/tenant/driver check still applies to the actual (non-preflight) request exactly as before — CORS only controls whether the *browser* is allowed to read the response, not whether the *server* processes the request.
- **Manually validated end-to-end by the developer**, combining both post-Phase-4 patches above: Expo Web opened at `http://localhost:8081`, the API was reachable at `http://localhost:8080` with the `local` profile active, the CORS preflight succeeded, DRIVER login succeeded, and the authenticated driver workflow (My Returns) rendered correctly in the browser. No physical-iPhone walkthrough was performed — the developer's installed Expo Go version is incompatible with this project's Expo SDK 57, unrelated to any code in this patch.

This confirmed product decision adds a required `productName` field across the backend, database, and mobile driver workflow — free text, one product per return (root CLAUDE.md §8 is unchanged: still exactly one product per return record), immutable after creation (no edit endpoint exists in any phase so far), and explicitly no product catalog, SKU, barcode, or ERP integration.

No compatibility alias was added, since no client shipped against `productDescription`.
- `V9__add_product_name_to_return_record.sql` follows V8's established temporary-default-then-drop pattern (`DEFAULT 'Unknown product'` added and immediately dropped after the `ALTER TABLE`) rather than assuming `return_record` is empty — safe regardless of whether local manual testing already created real rows. `VARCHAR(200) NOT NULL`, no product table, no speculative index. V1–V8 were not modified.
- `productName` is validated inside `ReturnRecordCreator` (trim, reject null/blank/whitespace-only/over-200-characters) via a new, dedicated `InvalidProductNameException` — deliberately not a reuse of `InvalidObservationException`, keeping each field's rejection independently traceable in logs and tests, consistent with every other field-specific exception in this module. The mobile `CreateReturnPayload`/`ReturnRecord` types and `returnValidation.ts` mirror the same 200-character limit and required/trim rules as every other client-validated field, for immediate UX feedback only — the backend remains authoritative.

**Return photos (Phase 5A):**

- **Phase 5's originally planned backend/mobile layer split is superseded by a feature split, per explicit instruction:** the roadmap previously planned "5A — media and signature backend" then "5B — mobile photos and customer signature." This phase instead delivers the complete photo vertical slice (backend and mobile together) as 5A, leaving 5B as the complete customer-signature vertical slice — `docs/IMPLEMENTATION_PLAN.md` §12/§13 updated accordingly, without renumbering any other phase.
- `storage.ReturnMediaStorage` is a two-method interface (`store`/`read` a binary object by server-generated key) — deliberately minimal, no delete/list/presigned-URL capability, since nothing in this phase needs them. `storage.FilesystemReturnMediaStorage` is the only implementation: it resolves every key against a configured root and verifies the result stays inside it (defense-in-depth against path traversal, even though every key is always server-generated, never a client filename). Chosen over MinIO for local-dev MVP simplicity — root CLAUDE.md §14 and `apps/api/CLAUDE.md`'s `storage` module section both now note this as the current Phase 5A choice, with MinIO/Cloudflare R2 remaining valid future implementations of the same interface. `app.storage.return-media.root` defaults to a repository-external `${user.home}/.returnflow/media` (so no `.gitignore` change was needed — no path under this checkout is ever used) and is a required, no-default environment variable in the `prod` profile, since a container's own filesystem is not durable across deploys.
- `V10__create_return_photo.sql` adds one new table, `return_photo` (tenant/return foreign keys, `storage_key` unique, `(return_record_id, photo_position)` unique, `photo_position` checked to `1..5`, `size_bytes` checked positive) — no product-table-style backfill was needed since this is a brand-new table, not a new column on an existing one. The Java field is `position`; the physical column is `photo_position`, not `position`, because `POSITION` is a reserved SQL keyword/function in PostgreSQL — the same deliberate Java/DB name split already established by `ReturnRecord.reasonDetails`/`other_reason_details`. `ReturnPhoto` does not extend `common.audit.Auditable`: the record is immutable after creation, so a meaningful `updatedAt` doesn't exist — only `createdAt` is stored, set once in the constructor. V1–V9 were not modified.
- **Five-photo limit and position assignment are made safe under concurrency by row-locking the parent return, not by a naive count-then-insert:** `ReturnRecordRepository.findByIdAndTenantIdAndDriverIdForUpdate` issues `SELECT ... FOR UPDATE` (via `@Lock(PESSIMISTIC_WRITE)`) before `ReturnPhotoService.upload` counts existing photos and assigns the next position — this serializes concurrent uploads to the *same* return (uploads to different returns never block each other) so two requests can never both observe "4 photos" and both write position 5. The database's `uk_return_photo_return_position`/`chk_return_photo_position_range` constraints remain a backstop beneath this, not a substitute for it. Proven with a real multi-threaded MockMvc test against Testcontainers Postgres: 8 concurrent uploads to one return always produce exactly 5 successes (`201`) and 3 conflicts (`409`), with positions landing on exactly `1..5`.
- `image/jpeg` is validated two ways, not just by the client-declared multipart `Content-Type` header (which can be spoofed): `ReturnPhotoService` also sniffs the real JPEG magic bytes (`FF D8 FF`) before accepting the upload — cheap enough to need no image-processing library. File size is enforced twice too: `spring.servlet.multipart.max-file-size=5MB` rejects an oversized part before it reaches application code, and `ReturnPhotoService` independently re-checks 5 MB as a backstop; both paths return the same safe `400 Invalid Photo File` rather than a `413`, chosen after discovering in testing that Spring's container-level multipart-size enforcement isn't reliably exercised through `MockMvc`'s `multipart()` builder — one consistent status was judged better than a status that depends on which layer happened to catch it.
- The photo endpoints live in a new `DriverReturnPhotoController`/`ReturnPhotoService`, not added onto the existing `DriverReturnController`/`DriverReturnService` — multipart handling and binary streaming were judged distinct enough to keep the original return CRUD controller uncluttered. Their `ProblemDetail` mappings were added to the existing `DriverReturnExceptionHandler` (same `@Order(HIGHEST_PRECEDENCE)` module-level advice), not a new advice class, since photos are still the `returnrecord` feature module. `ReturnResponse.photos` is populated by `DriverReturnService` re-querying `ReturnPhotoRepository` per return for list/detail (acceptable N+1 at this driver-scoped, small-list MVP scale) and is always `List.of()` on create (a just-created return cannot yet have photos, so no query is needed there).
- `ReturnPhotoResponse` exposes only `id`, `contentType`, `sizeBytes`, `position`, `contentPath` (an API-relative path like `/api/v1/driver/returns/{returnId}/photos/{photoId}/content`, never an absolute/localhost URL and never a token in the query string), and `createdAt` — never `storageKey`, `tenantId`, `driverId`, or a filesystem path. The content endpoint sends `Cache-Control: private, no-store` and a generic `Content-Disposition: inline; filename="return-photo.jpg"` that never echoes the storage key.
- Mobile normalizes every photo to JPEG before upload with `expo-image-manipulator`'s `manipulateAsync` (resize only above a 1600px longest edge, ~0.8 compression) — the simpler, if formally deprecated, one-call API was chosen over the newer contextual `ImageManipulator.manipulate().resize().renderAsync()` chain for MVP simplicity; both remain part of the same installed package, so switching later needs no new dependency. Normalization requests `base64` output purely to measure the exact resulting byte size before upload (no `expo-file-system` dependency was added for this); the uploaded file itself is still the manipulator's own output file (`uri`), never the base64 string, so upload is not a re-encode. `apps/mobile/src/api/apiClient.ts`'s JSON and multipart paths now share one `authorizedRequest` retry/refresh implementation (extracted, not duplicated) — multipart requests set no `Content-Type` header at all, letting `fetch` generate its own boundary; setting one manually would have made the server unable to parse the request.
- `AddReturnPhotosScreen` auto-uploads each photo immediately after on-device normalization rather than requiring a separate manual "upload" step — matches "local preview, then upload progress" more directly than a batch-review-then-submit flow, and keeps the five-photo limit checked against `existing + queued`, not just existing, before allowing another pick. A photo can only be removed from the queue during its brief `normalizing` state (before the upload request itself starts) — found in testing that without an explicit removed-ID guard, a slow normalize could resurrect a photo the user had already removed and still upload it after the fact; fixed by tracking removed local IDs in a ref checked right after normalization resolves, before the upload call.
- `CreateReturnScreen` now navigates (`replace`, not `navigate`) to `AddReturnPhotos`, not `ReturnDetails`, after a successful submission — Skip and Finish on that screen both `replace` to `ReturnDetails` either way, so the net effect for a driver who immediately skips is unchanged from Phase 4, but one who wants to add photos never has to navigate back through the list first.
- **Expo Web multipart upload correction (found in manual browser validation):** `returnService.uploadReturnPhoto` originally appended the same React Native-style `{ uri, name, type }` object as the file part on every platform. That representation is meaningful only to React Native's own `fetch`/`FormData` implementation, which streams the referenced local file directly; Expo Web uses the browser's real `fetch`/`FormData`, which has no special handling for a plain object and silently coerces it, producing a multipart request with no genuine file part — the backend correctly rejected it as missing. Fixed with a `Platform.OS` branch in `uploadReturnPhoto`: web now reads the normalized photo's URI through the browser's own `fetch` into a real `Blob` (stamped with `image/jpeg` if the browser reported something else) and appends that with an explicit filename; native behavior is untouched. Proven with `Platform.OS` swapped per-test (`Object.defineProperty(Platform, 'OS', ...)`) so both code paths are exercised directly, rather than only through UI-level mocks that would have hidden the platform branch entirely.
- **Uploaded-count and Finish-gating correction (same manual validation):** the screen previously displayed `uploadedPhotos.length + queue.length` as "N of 5 photos" — inflating the count with photos still uploading or already failed — and gated Finish on `uploadInProgress` alone, so a failed selection never blocked it. Now the displayed count ("N of 5 photos uploaded") reflects only `uploadedPhotos.length`; a separate `capacityUsed` (uploaded + queued) still gates whether another photo can be selected, unchanged; and Finish is disabled whenever the queue is non-empty for any reason (uploading, normalizing, or failed), not just while a request is active — Skip remains available in all of those cases except an actively in-flight upload, since skipping never claims a failed photo succeeded. A ref-tracked in-flight-upload guard (`inFlightUploads`) was also added so a fast repeated tap on Retry can never start two uploads for the same photo.

**Customer signature (Phase 5B):**

- **Normalized vector strokes travel as JSON instead of a client-generated image, and the backend is the only thing that ever renders the actual picture:** the mobile client sends only a signer name and an array of strokes (each an ordered list of `{x, y}` points in `[0, 1]`) — never Base64, PNG/JPEG bytes, or client-supplied SVG/HTML. `ReturnSignatureService` validates the strokes (signer-name length, stroke/point-count limits, coordinate finiteness/bounds, and a documented minimum total normalized drawn-length threshold — `0.05` — to reject an effectively blank tap even though it technically has "two distinct points") before handing already-validated points to `SvgSignatureRenderer`, a small component that emits a fixed, deterministic `image/svg+xml` document (white background rect, one `<path>` per stroke, rounded caps/joins, no scripts, no external resources, no client-provided markup — every byte of the output is server-written). This is a deliberate deviation from root `CLAUDE.md` §13's original "PNG" wording; §13 has been updated (new §13.1) to describe this as the model for any future signature capture, including the eventual warehouse signature.
- `ReturnSignature` mirrors `ReturnPhoto`'s conventions exactly (immutable, package-private constructor, no `Auditable` base, only `signedAt`) and reuses `ReturnRecordRepository.findByIdAndTenantIdAndDriverIdForUpdate` — the same pessimistic row lock Phase 5A's photo uploads already use — so a concurrent signature submission for the same return can't also observe "no signature yet" and insert a second one; `V11__create_return_signature.sql`'s `uk_return_signature_return_record` unique constraint is the database backstop beneath that. Proven with the same multi-threaded MockMvc-against-Testcontainers pattern Phase 5A used for photos: 8 concurrent submissions to one return always produce exactly one `201` and seven `409`s.
- `ReturnResponse.signature` is nullable and reused across create/list/detail via one `signatureFor(...)` helper mirroring `photosFor(...)` — always `null` on create (a just-created return cannot yet have one, so no query is needed), populated by re-querying `ReturnSignatureRepository` for list/detail. Clients read "pending" from that nullability rather than a separate boolean flag, per this task's own explicit instruction not to create contradictory state.
- Mobile's `SignaturePad` is a custom `react-native-svg` + `PanResponder` component, not a WebView-based signature library or a browser-only canvas package — works identically on native and Expo Web. It is uncontrolled (owns its strokes internally, reports every committed stroke via `onStrokesChange`) and exposes `clear`/`undoLast` imperatively via `ref`, since those are triggered by buttons outside the pad's own touch area. Point-density filtering (a `0.01` normalized minimum distance between consecutively recorded points) keeps a long, slow gesture from recording an excessive number of near-duplicate points; a stroke with fewer than two points (a tap) is discarded on release rather than committed.
- An explicit `AddReturnPhotos.origin` navigation parameter (`'created' | 'details'`), not navigation-history inference, decides where Skip/Finish lead: `'created'` (the primary new-return flow, set by `CreateReturnScreen`) goes to `CustomerSignatureScreen` next; `'details'` (the secondary "add more photos later" flow from Return Details) returns to Return Details, unaffected by signature state — a signed return is never asked to sign again, and a still-pending one is reachable again only through Return Details' own explicit `Capture customer signature` action, not automatically re-triggered by a secondary photo edit.
- Remote authenticated rendering of the signature image itself is deferred, not implemented, in this phase — Return Details and My Returns show only safe metadata (signer name, captured/pending state, timestamp), the same scope decision Phase 5A made for photo thumbnails and for the same reason (avoiding a token in a URL / broad platform-specific image-loading infrastructure for an MVP phase).
- No `DRAFT` return status was added, and no existing return status changed — a return with a pending signature is simply `AWAITING_WAREHOUSE` with `signature: null`, resumable at any time from Return Details without creating a second `ReturnRecord`.

**Phase 6B1 — Web foundation and ADMIN authentication:**

- **Access token in memory only; refresh token in `sessionStorage` only, under one narrowly named key** (approved MVP strategy) — never `localStorage`, never a cookie the frontend invents, never in a URL. A page reload always loses the in-memory access token by design; session restoration re-derives it by calling `/auth/refresh` with the persisted refresh token, then `/auth/me`. Closing the browser tab/session ends the ADMIN's session (`sessionStorage` is cleared by the browser) — accepted as safer than indefinite `localStorage` persistence for this MVP.
- `api/apiClient.ts` mirrors the mobile app's proven `authorizedRequest` pattern (module-level session state, a single de-duplicated in-flight refresh promise, retry-exactly-once-on-401) rather than inventing a new design — the two clients solve the same problem (short-lived access token, longer-lived rotating refresh token) and diverge only in where each platform is allowed to persist the refresh token (Expo SecureStore vs. `sessionStorage`).
- **Concurrent 401s share one refresh call**: `refreshOnce()`'s in-flight promise is cached at module scope, so two callers hitting an expired access token at the same moment trigger exactly one `/auth/refresh` request and one token rotation, not two competing rotations.
- **The authenticated user's identity and role authority come from `/auth/me`, never from client-decoded JWT claims** — the access token is treated as an opaque bearer credential the browser never inspects, consistent with root `CLAUDE.md` §24 (authorization is server-enforced) and avoiding a second, driftable place that "knows" the role.
- **Local development uses a Vite dev-server proxy (`/api` → `http://localhost:8080`), not an expanded backend CORS allowance** — the browser sees a same-origin relative path, so no `apps/api` change was needed for this phase (unlike Expo Web, which genuinely crosses origins and needed the existing `local`-profile CORS rule). `VITE_API_BASE_URL` remains available to point at a real, different-origin API in deployment.
- **The Vite proxy normalizes the forwarded `Origin` header to its own backend target (`http://localhost:8080`), found during manual Chrome validation:** Vite's `changeOrigin: true` only rewrites the `Host` header, not `Origin` — the browser's real `Origin: http://localhost:5173` was reaching Spring Boot unchanged, and since the `local`-profile CORS rule deliberately allows only `http://localhost:8081` (Expo Web), every proxied browser request was rejected with `403` before reaching `AuthController` (confirmed by zero application-level query activity in the backend log for the rejected requests). Fixed entirely inside `apps/web/vite.config.ts`'s existing `/api` proxy entry with a static `headers: { Origin: 'http://localhost:8080' }` override — no new dependency, no custom proxy server. With the proxied request's `Origin` matching its own target host, Spring's `CorsUtils.isCorsRequest` treats it as same-origin and never invokes CORS checking at all, so **backend CORS and backend source remain untouched** — this is local-development Vite configuration only and has no effect on production authentication behavior (a deployed web app calls a real, separate-origin API via `VITE_API_BASE_URL` and goes through actual CORS, not this proxy).
- **TanStack Query is installed as server-state/cache infrastructure only** — Phase 6B1 has no operational query yet (Dashboard/Returns/Users/Routes are static placeholders that call no API), but `AuthProvider` already calls `QueryClient.clear()` on logout so the cache-clearing contract exists before Phase 6B2 adds real queries to clear.
- **An open-redirect guard (`routes/safeRedirect.ts`) sanitizes the "return to this route after login" destination** — `ProtectedRoute` remembers the attempted path in router location state, but that state is treated as untrusted input; only a same-origin path starting with a single `/` is honored, rejecting protocol-relative (`//host/...`) or backslash-obfuscated values and falling back to `/dashboard`.
- **The Login page shows exactly one generic message for any invalid-credentials response**, regardless of the backend's specific `ProblemDetail` (inactive account, unknown email, wrong password all reach the same `AuthExceptionHandler`-produced 401 today) — this re-collapses server-side messages further, per this phase's explicit instruction never to distinguish those cases in the UI even if a future backend change made the messages more specific.
- Reusable components introduced only where real reuse exists (per `apps/web/CLAUDE.md`): `FullPageLoading`, `ErrorMessage`, `ProtectedRoute`, `AppShell` — no broader component library.
- **A known npm-audit advisory on `react-router` (GHSA-qwww-vcr4-c8h2, "RSC Mode CSRF Bypass") affects the installed `react-router-dom@7.18.2` and has no non-breaking fix at this time** (`npm audit fix --force` would downgrade to a pre-7.12 release) — the vulnerability is specific to React Router's RSC ("framework mode") data-loader/server-actions integration, which this plain client-side SPA (a `BrowserRouter` with no server-rendered loaders/actions) never uses. Not force-fixed, consistent with root `CLAUDE.md` §39.7a and the same judgment already applied to `apps/mobile`'s own unfixable transitive advisories — see Known issues.
- `@testing-library/react`'s automatic per-test `cleanup()` needs either `test.globals: true` or an explicit registration; this project deliberately imports Vitest APIs explicitly rather than enabling globals, so `src/setupTests.ts` now calls `afterEach(cleanup)` itself — found because several new tests were intermittently seeing "multiple elements" failures from a prior test's un-cleaned-up DOM inside the same file.
- No `@testing-library/user-event` was added (not already present, and not in this phase's approved-dependency list) — component interaction tests use `fireEvent` plus `act` instead.

- **No frontend sort control exists anywhere** — the backend's fixed `createdAt` descending, `id` descending order is the only order either table ever shows.
- **Australia/Sydney is explicit wherever a "today" or a displayed timestamp is involved**, never the browser's local timezone: `returns/sydneyDate.ts`'s `todaySydneyDate()` (used only to build the Returns Today shortcut's `createdFrom`/`createdTo` query values) and `formatSydneyTimestamp()` (used for every displayed `createdAt`) both pass an explicit `timeZone: 'Australia/Sydney'` to `Intl.DateTimeFormat` — mirroring the backend's own `OperationalDayService` business timezone. Neither function computes a UTC boundary itself; the server remains the sole authority for converting a local date into the actual UTC instant range.
- **In Review and Closed Today render the real API value but are permanently non-clickable and marked "Available with warehouse review"** — until Phase 7A adds the `IN_REVIEW`/`CLOSED` statuses and a close timestamp, showing them as ordinary clickable `0` counts would misrepresent a metric that doesn't exist yet. `SummaryCard`'s `disabled` prop suppresses the `onClick` regardless of whether a handler was passed, so this can't be accidentally re-enabled by only removing the `secondaryText`.
- **The Returns page's driver/route filter dropdowns reuse the existing read-only `GET /admin/users`/`GET /admin/routes` endpoints exactly as they are** — `useDriverOptions` filters the full user list to `role === 'DRIVER'` client-side (no dedicated "drivers only" backend endpoint exists, and none was needed). No create/edit/deactivate control, no user- or route-management page — Phase 8 remains unimplemented.
- **Every Returns list filter/search/page value lives in the URL query string, parsed and sanitized by `returns/filters.ts`** — `parseReturnsFilters` individually validates each field (known enum value, `YYYY-MM-DD` pattern, UUID pattern, non-negative integer) and silently falls back to "no filter" for anything else, so a hand-edited URL, a stale bookmark, or a future backend enum value this build doesn't know about can never reach the API as garbage or crash the page.
- **`TanStack Query`'s query keys include every filter/page parameter** (`returnsListQueryKey`), so each distinct filter combination is its own cache entry — this, not manual request cancellation/`AbortController` wiring, is what actually prevents a fast filter change from ever displaying an in-flight older request's stale result over a newer one. `placeholderData: keepPreviousData` (TanStack Query v5) keeps the previous page's rows visible during a page/filter transition instead of flashing a loading state.
- **Search commits on explicit submit, not per keystroke; the date-range inputs commit on blur** — both keep uncommitted local draft state so typing never triggers a request, matching this phase's explicit "prefer the simpler implementation that keeps URL state predictable" instruction over a debounce.
- **The invalid-date-range check (`createdFrom` after `createdTo`) runs client-side purely for immediate feedback and blocks the request from ever being sent** — the backend independently re-validates the same rule regardless.
- **Return Details and authenticated photo/customer-signature retrieval remained entirely unimplemented in this slice** — `ReturnTable` rows were deliberately not links; Phase 6B2B (below) activated Return # navigation once the page they point to actually existed.
- No new dependency was needed for this phase — `react-router-dom`'s `useSearchParams` and `@tanstack/react-query`'s existing v5 APIs (`keepPreviousData`, `refetchInterval`, `refetchIntervalInBackground`) already covered every requirement.

**Phase 6B2B — Return Details and authenticated media display:**

- **The Return # in Latest Returns and the Returns table is now a real link to `/returns/{returnId}`** — `ReturnTable` accepts an optional `backTo` prop (the current table's own path+query) passed as router `state.from` on every row's link, so Return Details' "Back to Returns" can return to the exact filtered view rather than a bare `/returns`; the Returns page passes its own `location.pathname + location.search`, the Dashboard's Latest Returns passes nothing (no meaningful list context to preserve there). The `state.from` value is sanitized through the same `routes/safeRedirect.ts` `sanitizeRedirectTarget` guard `ProtectedRoute` already uses for post-login redirect — one open-redirect guard, not two independently-written ones.
- **Private ADMIN media (photos, the rendered customer signature) is fetched through a new `authorizedRequestBlob` export on the existing `api/apiClient.ts`**, not a new HTTP client — it is the same `authorizedRequest` function every JSON call already goes through (bearer-token attachment, one shared/deduplicated refresh-and-retry on 401, session-expiry handling), just reading the response as a `Blob` via the `responseType: 'blob'` option that already existed in `RequestOptions` since Phase 6B1. A plain `<img src="...">` cannot reach this endpoint at all: the access token is intentionally memory-only (Phase 6B1) and never available to place in a URL.
- **A backend `contentPath` (e.g. `/api/v1/admin/returns/{id}/photos/{photoId}/content`) already includes the API version prefix, so it is never concatenated directly with `getApiBaseUrl()`** — that would produce `/api/v1/api/v1/...` locally, or the wrong host once `VITE_API_BASE_URL` is an absolute deployment URL. `config/environment.ts`'s new `toApiRelativePath` strips the known `/api/v1` prefix first, so the remainder resolves correctly through the exact same base-URL logic as every other endpoint path in this app — proven for both the local relative default and an absolute deployment base in `environment.test.ts`.
- **Fetched media bytes become a `Blob`, converted to a `URL.createObjectURL` object URL for the `<img>` tag, and revoked on unmount/re-fetch** (`components/AuthenticatedImage.tsx`) — never Base64, never persisted to `localStorage`/`sessionStorage`, never kept in memory longer than the page needs it (`useMediaBlob`'s `gcTime: 0`/`staleTime: 0` deliberately does not retain a private, potentially multi-megabyte Blob in the TanStack Query cache after nothing is displaying it — unlike this app's small JSON queries, which keep the library's normal defaults).
- **The backend-generated SVG signature is rendered exactly like a photo — as an `<img>` backed by an authenticated Blob object URL — never `dangerouslySetInnerHTML`, never an `<iframe>`/`<embed>`/`<object>`.** The browser's own image decoder handles the bytes; the HTML parser never sees them, regardless of what the response actually contains.
- **Each `AuthenticatedImage` instance owns its own query and failure state, keyed by the caller (`key={photo.id}` in the gallery)** — one photo's fetch failure shows only that slot's inline "Unable to load this image." + Retry, never a page-level error, and never hides a sibling photo, the signature, or the rest of Return Details.
- **A malformed `returnId` route parameter is validated client-side (`returns/filters.ts`'s exported `isValidUuid`) before any request is made** — a clearly-invalid ID renders the identical "This return could not be found." state a real backend 404 would, without ever reaching the API; this reuses the same UUID pattern the Returns page's `driverId`/`routeId` filter sanitization already validates against, not a second regex.
- **The "not found" message is always the fixed, approved wording, never the backend's own `ProblemDetail.detail`** — a 404 is special-cased ahead of the generic `toSafeErrorMessage` fallback specifically so a real backend detail string (e.g. "Return not found.") never substitutes for the product-approved copy from `docs/WEB_UX.md` §10.
- **Return Details is strictly read-only, matching root `CLAUDE.md` §9.1/§17.3 and this phase's explicit scope**: no Start Review, Close, Cancel, Release, Takeover, reviewer, warehouse decision fields, warehouse signature, or PDF action exist anywhere on the page — opening it has zero mutation side effects, and nothing here anticipates Phase 7A/7B/8/9 fields that don't exist in the domain yet.
- No new dependency was needed for this phase either — the existing API client, TanStack Query, and the browser's native `URL.createObjectURL`/`Blob` covered every requirement.

**`chore/fix-local-frontend-startup` — a small follow-up DX fix to the script above, not a product phase:**

- **The frontend now launches attached directly to the console `.\dev.ps1` was run from, instead of opening its own separate "ReturnFlow Web (local)" window** (the backend is unaffected — it still opens its own separate window exactly as before). `Start-Frontend` calls `Start-Process -FilePath <resolved npm.cmd> -ArgumentList 'run','dev' -NoNewWindow -WorkingDirectory $WebRoot`, deliberately without `-Wait`: `-NoNewWindow` keeps Vite's stdout/stderr attached to the invoking console with no separate window/tab, and omitting `-Wait` lets the script continue immediately to its existing HTTP health check and final summary instead of blocking on a process that, as a dev server, never exits on its own. Vite keeps running attached to that console after the script itself finishes and hands control back to the developer; a one-line notice prints once the frontend comes up explaining that Ctrl+C in that console stops the frontend only and has no effect on the separately-windowed backend, since backend/frontend are genuinely separate OS console sessions.
- **Resolving `npm.cmd`'s and `node.exe`'s absolute paths explicitly — rather than relying on bare `npm run dev` — is preserved from the prior npm/node reliability fix and is not undone by this change.** A Windows Node.js install places an extensionless POSIX-shim file named `npm` alongside the real `npm.cmd` launcher in the same directory, which Windows has no execution handler for at all; and `npm.cmd` itself internally invokes a further bare `node` command. `Resolve-NpmCommand`/`Resolve-NodeExecutable` (both via `Get-Command`, with a same-directory `.cmd`/`.exe` fallback, never hardcoded) resolve both paths once in the parent process; `Start-Frontend` invokes the resolved `npm.cmd` path directly via `-FilePath` (never a bare `npm` name) and defensively prepends the resolved Node directory to this script's own process-scoped `$env:PATH` first if not already present (never the persistent machine/user PATH) — the same defensive-PATH pattern `Start-Backend` already uses for `mvnw.cmd`'s inner `powershell` call, so both children stay protected the same way even though the frontend no longer runs inside its own spawned window.
- No other script guarantee changed: infrastructure/backend startup, reuse detection (an already-running frontend is still detected via its page title and reused, never duplicated), port-conflict handling, and the bootstrap-password-never-printed behavior are all untouched. `-NoProfile` is unchanged for the backend's own window; it no longer applies to the frontend at all, since the frontend no longer spawns a `pwsh`/`powershell` host of its own.
- Manually validated end-to-end from the repository root, twice: a fresh `.\dev.ps1` run (Postgres/MinIO/backend already healthy, frontend stopped first to force a genuine cold start) printed Vite's own startup output (`VITE vX ready`, `Local: http://localhost:5173/`) directly inline with the script's own output — no separate window opened — with no "npm is not recognized" and no "node is not recognized" error, `http://localhost:5173` served the real ReturnFlow app, and the full spawned process ancestry (resolved `npm.cmd` → npm's own internal `cmd.exe`/node wrapper → the `vite` script's own `cmd.exe` wrapper → `node.exe` running `vite.js`) was inspected directly to confirm both resolved paths were genuinely used and that no shell-host window process existed anywhere in that chain; Vite was also confirmed still running and still serving after the invoking process itself had exited. A second `.\dev.ps1` run correctly detected and reused both the backend and the now-running frontend, with exactly one process still owning each of ports 8080/5173 and exactly one `vite.js` process system-wide — no duplicates, no unrelated process touched.

**Phase 7A — Warehouse review backend:**

- **Every lifecycle mutation locks the target return with the same pessimistic-write pattern Phase 5A/5B already proved for photo/signature uploads** (`ReturnRecordRepository.findByIdAndTenantIdForUpdate`, tenant-scoped only — unlike the DRIVER-owned variant, ADMIN operations aren't scoped to a particular driver), not a bespoke locking mechanism. `ReturnRecord` also gained a `@Version` column (root `CLAUDE.md` §25 explicitly calls for optimistic locking) as a defense-in-depth backstop beneath that pessimistic lock, not a replacement for it — every existing row starts at version `0`, a permanently valid value, unlike V8/V9's temporary-default-then-drop pattern for genuinely user-facing fields.
- **Reviewer/closer/canceller are raw `UUID` columns on `ReturnRecord`, not `@ManyToOne` associations** — a deliberate departure from `tenant`/`driver`/`route`'s associations on the same entity (Phase 3A), which exist only because that entity uniquely references three aggregate roots at once. These three are optional, populated well after creation, and don't need that justification. Resolving a reviewer/closer/canceller's display name is a small `UserRepository.findByIdAndTenantId` lookup in a new shared `AdminReturnMapper`, not a fetched association.
- **Take Over Review's staleness guard is an expected-value compare-and-swap (`expectedCurrentReviewerId`), not a client-submitted `version` number** — the client sends the reviewer ID it last observed (e.g. from `AdminReturnDetailResponse.reviewer.id`); the request is rejected as a `Stale Takeover` conflict if the return's actual current reviewer has since changed. This is simpler than exposing and round-tripping the entity's internal optimistic-lock version through the API, and is exactly the value already naturally visible to an ADMIN reading the return.
- **A takeover's only audit trail is overwriting `reviewStartedBy`/`reviewStartedAt` again** — deliberately not a new event/history table, per this phase's explicit "do not build event sourcing" scope and the root `CLAUDE.md` §22.7 guidance that only `CREATED`/`CLOSED`/`CANCELLED` warrant even a minimal event model. The previous reviewer's browser-only, never-transmitted form state was never a backend concern to inherit.
- **The warehouse signature reuses `return_signature`/`ReturnSignatureService`'s architecture rather than a parallel `WarehouseSignature` entity/service**, per root `CLAUDE.md` §13.1's explicit instruction that the customer-signature approach is "the model for any future signature capture, including the eventual warehouse signature." `ReturnSignature` gained a `signature_type` (`CUSTOMER`/`WAREHOUSE`) discriminator column (V13, every existing row backfilled to `CUSTOMER` — the only kind that could have existed before this phase); its unique constraint became `(return_record_id, signature_type)`. Signer-name/stroke validation was extracted from `ReturnSignatureService` into a new stateless `SignatureStrokeValidator`, used identically by both the DRIVER customer-signature endpoint and the ADMIN Close endpoint — same limits, same exceptions (`InvalidSignerNameException`/`InvalidSignatureStrokesException`), same rejection of an effectively-blank drawing. `warehouseRepresentativeName` is not a separate column: like the customer side (`customerRepresentativeName` = `signature.signerName`), it's read back from the warehouse `ReturnSignature.signerName` — Close's `warehouseRepresentativeName` field doubles as that signature's signer name, so nothing is stored twice.
- **Close's required-field validation is almost entirely ordinary Bean Validation** (`@NotNull Boolean` for the four Yes/No decisions, `@NotBlank` for the representative name) reaching `GlobalExceptionHandler`'s existing `MethodArgumentNotValidException` handling — no new "missing field" exception class was needed. Only the deeper signature-stroke shape (empty/blank/out-of-bounds) needs service-level validation, exactly mirroring `CreateReturnRequest.reasonDetails`'s existing "structural Bean Validation, semantic domain validation" split.
- **New exception design keeps lifecycle-conflict messages specific without one class per transition**: `InvalidReturnLifecycleException(String message)` (409) covers every "wrong status for this action" case across all five endpoints — mirroring the existing `user.InvalidRouteAssignmentException` precedent — while `ReviewAlreadyClaimedException`/`ReviewOwnershipConflictException`/`StaleTakeoverException` each carry a `currentReviewerName` the `AdminReturnExceptionHandler` surfaces as a `currentReviewerName` `ProblemDetail` property, satisfying `docs/WEB_UX.md` §10's "show current reviewer's name, never allow a silent overwrite" without a generic error-data framework.
- **A real, unrelated gap was found and fixed while wiring the DRIVER-editing-restriction requirement**: neither `ReturnPhotoService.upload` nor `ReturnSignatureService.create` had ever checked the return's status — harmless through Phase 6A because `AWAITING_WAREHOUSE` was the only status that could ever exist, but a real hole now that `IN_REVIEW`/`CLOSED`/`CANCELLED` are reachable. Both now reject (409, new `ReturnNotEditableException`) outside `AWAITING_WAREHOUSE`, checked immediately after acquiring the existing per-return pessimistic lock, before any file/signature validation runs. Proven by dedicated tests: a photo upload and a signature-capture attempt are each rejected the moment `IN_REVIEW` begins, and again once `CLOSED`.
- **`AdminReturnMapper` centralizes every `ReturnRecord` → ADMIN-response mapping** (list item, detail, and the reviewer/closer/canceller name lookup), shared by the pre-existing read-only `AdminReturnService` and the new `AdminReturnReviewService` — extracted so the two services don't independently maintain the same photo/signature/reviewer-name mapping logic, especially now that every lifecycle endpoint returns the same `AdminReturnDetailResponse` shape the `GET` endpoint already produced.
- **Dashboard `inReview`/`closedToday` now compute from real data** — `inReview` is `countByTenantIdAndStatus(..., IN_REVIEW)` (the exact same query shape Phase 6A already used for `waitingWarehouse`); `closedToday` reuses `OperationalDayService`'s existing Australia/Sydney business-day boundary against a new `closed_at` column, proven correct with a real cross-day backdating test (a closed-yesterday return is excluded from today's count) — no new timezone logic was written.
- **The automated `AdminReturnReviewIntegrationTest` suite exercises every endpoint through real HTTP (`MockMvc`) against a real Testcontainers PostgreSQL instance, including a genuine 6-admin concurrent Start Review race** — this is the primary correctness guarantee for concurrency and tenant/role isolation, which a manual pass alone cannot reproduce. The developer additionally performed a manual Postman review of the full lifecycle against the real local backend (Start Review, non-owner-rejected and owner-accepted Release Review, expected-reviewer-guarded Take Over Review, Close with full warehouse field/signature persistence, terminal-state rejection of a `CLOSED` return, and Cancel), confirming the automated suite's behavior end-to-end through the real HTTP surface a web/mobile client would actually use — see Review status.

**Phase 7B — Warehouse review web workflow (approved 2026-08-14):**

- **The review lifecycle lives inside the existing `ReturnDetailsPage`, not a parallel review route or page** — the same file already owned the read-only display of driver/photo/customer-signature data (Phase 6B2B); adding lifecycle sections keyed on `detail.status` kept one page as the single source of truth for a return's full picture, matching the explicit instruction not to create a parallel review page. `ReturnDetailsContent` grew several small, purely-presentational helper components in the same file (`WarehouseReviewForm`, `ClosedWarehouseSummary`, `CancelledSummary`) rather than new files, mirroring this file's existing single-file-page convention; only the genuinely reusable primitives (`ConfirmDialog`, `YesNoField`, `WarehouseSignaturePad`) became new `components/` files, per `apps/web/CLAUDE.md`'s "create components only after reuse is real."
- **Ownership is derived from `useAuth().user.userId === detail.reviewer.id`, never a client-decoded token or a separately-tracked "am I the owner" flag** — the same identity source root `CLAUDE.md` §24/`docs/WEB_UX.md` §4 already establish for this app (the authenticated user comes from `/auth/me` via `AuthContext`, not JWT claims). This is also why `auth/AuthContext.tsx`'s `AuthContext` object itself is now exported (previously module-private): `ReturnDetailsPage.test.tsx` needs to supply a fixed, already-authenticated `AuthContextValue` directly via `<AuthContext.Provider>` for dozens of lifecycle scenarios, which is far simpler and faster than re-running `AuthProvider`'s real session-restoration network flow (`/auth/refresh` + `/auth/me`) in every one of them — a test-only export, no runtime behavior changed.
- **Every lifecycle mutation (`useStartReview`/`useReleaseReview`/`useTakeOverReview`/`useCloseReturn`/`useCancelReturn`) writes its response straight into the TanStack Query detail cache via `setQueryData`, then invalidates the returns list, Latest Returns, and dashboard summary queries** — the mutation response is already the authoritative post-transition `AdminReturnDetailResponse` (same shape `GET` returns), so there is no need to wait on a second round-trip to show the new state on this page; the three broader invalidations exist because a status/reviewer change on one return can change counts and rows shown elsewhere, and none of those queries carry enough context to be patched in place safely. On a 409 conflict, the mutation deliberately does *not* touch the cache — the page instead calls `detailQuery.refetch()` explicitly, so a stale local view is never silently overwritten by an optimistic write.
- **`WarehouseSignaturePad` is plain React + inline SVG + native Pointer Events — no drawing/signature dependency was added**, mirroring `apps/mobile`'s `react-native-svg`/`PanResponder`-based `SignaturePad` but built on the browser's own unified pointer-event model (mouse/touch/pen) instead of a React Native gesture library. It records normalized (0..1) points via `getBoundingClientRect()`, exposes `clear`/`undoLast` imperatively via `ref` (buttons live outside the drawing surface), and sends only those normalized stroke points as JSON on Close — never SVG markup, HTML, Base64, or image bytes; the backend remains the only renderer of the stored SVG, unchanged from the Phase 5B customer-signature model. `returns/signatureValidation.ts` duplicates (not imports — the two apps deliberately share no UI/data code) the backend's exact `SignatureStrokeValidator` limits, including the `0.05` normalized minimum-drawn-length threshold, for immediate client-side feedback only; the backend independently re-validates and remains authoritative.
- **The four required warehouse Yes/No decisions use `boolean | null` in local form state, driven by a radio-group `YesNoField` component, specifically so "unanswered" and "answered No" are distinguishable** — a plain `boolean` (defaulting `false`) or a checkbox would have silently treated an untouched decision as a `No` answer; Close's client-side validation checks each of the four for `=== null` before allowing the confirmation dialog to open, and the same shape (`sellable: boolean | null`, etc.) travels unchanged into the request body only once all four are non-null.
- **No autosave, no draft persistence, no `localStorage` for review-form values, anywhere** — matches `docs/WEB_UX.md` §8's Resolved MVP decision exactly. The warehouse form is plain component state (`useState`) that resets whenever `detail.reviewStartedAt` changes (a fresh Start Review or a Take Over Review always advances it), which is what guarantees a new reviewer — including the same admin re-claiming a review — never inherits a previous reviewer's unsaved values, because none were ever transmitted or stored anywhere the new session could read them from.
- **Unsaved-form protection covers `beforeunload` and every product-controlled in-app navigation trigger, through one shared mechanism, not a generic form-draft/navigation-blocking framework** — found in initial review to be too narrow (only Return Details' own "Back to Returns" was protected; `AppShell`'s Dashboard/Returns/Users/Routes nav links were not) and corrected within this same Pending Review cycle. A new `routes/navigationGuard.tsx` (`NavigationGuardProvider`/`useNavigationGuard`, mounted once by `AppShell` around its own nav and `<Outlet>`) holds exactly one boolean (`isDirty`) and one pending-action callback — no persisted draft, no `localStorage`, nothing beyond what a single confirmation dialog needs. `ReturnDetailsPage` mirrors its own `formDirty` into the guard via a plain `useEffect` (the form itself remains the single source of truth; the guard only ever reflects it) and clears it on unmount. `AppShell`'s new `GuardedNavLink` wraps each nav `NavLink`, intercepting its click only while dirty (preserving native middle-click/ctrl-click "open in new tab" for the ordinary, non-dirty case) and routing through the same `guardNavigation(...)` Return Details' "Back to Returns" link now also calls — one implementation of "ask before leaving," reused by both trigger points. **The browser Back button remains deliberately unprotected**: `apps/web` uses a plain `<BrowserRouter>` (not a data router), so React Router's `useBlocker`/`unstable_usePrompt` — the only clean way to intercept Back — require a `createBrowserRouter`/`RouterProvider` migration; the alternative (pushing/popping synthetic history entries to trap `popstate`) is exactly the "brittle history manipulation" this phase was explicitly told not to build. Revisit only if a future phase migrates to a data router for other reasons — see Known issues.
- **The Dashboard's Closed Today card filters on a real `closedFrom`/`closedTo` range, matching its own `closedAt`-based count exactly** — found in initial review to instead reuse `createdFrom`/`createdTo` (a return created on an earlier day but closed today would be counted but not shown), which `docs/WEB_UX.md` §5's "Opens `/returns` filtered to closed + today" already specified against, so this was treated as the blocking API-contract gap it was, not masked client-side. The smallest correct fix added the minimum backend surface: `closedFrom`/`closedTo` on `GET /api/v1/admin/returns`, filtering on `closed_at` (see the `apps/api` capabilities entry above) — mirrored on the web side by `returns/filters.ts`'s `ReturnsFilters.closedFrom`/`closedTo` (parsed/serialized exactly like `createdFrom`/`createdTo`, including URL round-tripping and `hasActiveFilters`) and `returns/api.ts`'s `ReturnListParams`. **No dedicated filter-bar input exists for this dimension** — it is reachable only through the Dashboard shortcut's URL, the same way every other filter here is URL-addressable; adding a user-facing "Closed from/to" control was not requested and would have expanded scope beyond the reported issue. `createdFrom`/`createdTo` and `isInvalidDateRange` are completely unchanged — the two date ranges are independent and neither replaces the other.
- **Cancel Return is available to any authenticated ADMIN from `AWAITING_WAREHOUSE` or `IN_REVIEW`, including a return `IN_REVIEW` under a different admin's ownership** — verified directly against `AdminReturnReviewService.cancel(...)`, which performs no reviewer-ownership check at all (only a status check), so the web client deliberately does not add a client-only ownership restriction that would contradict the real backend contract.
- **`toReviewConflictMessage` (new, `api/problemDetail.ts`) appends the backend's `currentReviewerName` `ProblemDetail` property to the existing safe-message fallback** rather than a bespoke per-action conflict-formatting function — one small helper covers Start Review's "already claimed," Release/Close's "ownership conflict," and Take Over Review's "stale takeover" 409s uniformly, since all three carry the same optional property.

No dependency, no redesign, no lifecycle behavior change — `ConfirmDialog` is the one shared implementation behind Close/Cancel/Release/Take Over/"Leave this return?", so fixing it there fixed all five call sites at once.
  - `CLOSED` Return Details' `ClosedWarehouseSummary` already received `reviewStartedAt` on its `detail` prop but never rendered it. Added a "Review started at" row (Sydney time, via the existing `formatSydneyTimestamp`), guarded the same way the neighboring "Reviewed by"/"Closed at" rows already are — no backend change, since `reviewStartedAt` was already part of the `AdminReturnDetailResponse` contract.

Added a small "Closed today" indicator (`ReturnsListPage`, new `.active-filter-chip` style) shown whenever either value is present, with its own "×" control that clears only `closedFrom`/`closedTo` (via the existing `applyFilters` helper) and leaves every other active filter untouched; the existing "Clear filters" action already cleared both values (they were already part of `EMPTY_FILTERS`) and needed no change. - **Phase 8 is a pure `apps/web` slice over the already-approved Phase 2C endpoints — no backend source change was needed or made.** The contract was read directly from `UserAdminController`/`UserAdminService`/`RouteAdminController`/`RouteAdminService` and their DTOs rather than assumed, and the two list endpoints return a plain array, so **no server-side pagination was added on either side**: introducing a `PageResponse` contract for a single-tenant pilot's user/route lists would have been a backend change this phase explicitly did not need. Client-side search over the already-loaded user list covers the real need.
- **The backend's own rules are mirrored client-side for immediate feedback, never re-invented or contradicted**: an ADMIN must have no route (the field is hidden, and switching DRIVER→ADMIN clears any selection so a stale value can't be sent), and a DRIVER needs a route only when the resulting user will be active — exactly `UserAdminService.validateRouteAssignment`'s `resultingActive` logic, including its allowance for an inactive DRIVER without one. The backend remains authoritative and re-validates everything; each rule was verified against the real running API and returns the exact `ProblemDetail` text the UI displays (see Review status).
- **Only ACTIVE routes are assignable, with one deliberate exception**: a DRIVER whose assigned route has since been deactivated keeps that route visible and selected, labelled inactive. Filtering it out would have silently presented a different route as the user's current state; leaving it visible shows the truth and lets the ADMIN resolve it deliberately (reassign, or deactivate the driver), which is the same "never silently fix an invalid state for the ADMIN" stance the route-deactivation conflict below takes.
- **A blocked route deactivation (409 `Route In Use`) keeps the ADMIN's typed values and surfaces the backend's own explanation** — the edit dialog reopens with its state intact rather than closing or reporting success. Nothing client-side attempts to reassign or deactivate the dependent drivers to make the deactivation succeed: that is a real operational decision, not a workaround the UI should perform on the ADMIN's behalf.
- **Deactivation is confirmed at Save time by comparing the authoritative record's `active` against the form's**, not by a separate deactivate button — active→false opens one confirmation before anything is sent, while reactivation and ordinary name/email/route edits save directly. This keeps a single edit path (one full PUT) instead of a parallel activate/deactivate action that would duplicate the same request.
- **Self-protection disables only the two controls the backend actually rejects** (own role change, own deactivation), with a plain explanation — no client-side permission model was introduced, and the backend's `SelfDeactivationException`/`SelfRoleChangeException` messages are still displayed verbatim if they are ever reached another way.
- **Password material is confined to component state for the shortest possible time**: it is never logged, never written to `localStorage`/`sessionStorage`, never placed in a query cache (the reset mutation deliberately invalidates nothing and the backend answers 204), never echoed back after success, and is cleared whenever its dialog closes. The reset request carries only `newPassword`, matching `ResetPasswordRequest` exactly — the existing password is never requested, sent, or displayed, because it genuinely cannot be read back.
- **`ConfirmDialog` gained one additive optional prop, `dismissOnBackdropClick` (default `true`)**, so every pre-existing confirmation behaves exactly as before while the new administration form dialogs opt out. A form holding several typed fields — including a password — should not be discardable by a stray click outside it; that is data loss, not a dismissal.
- **A minimal client-side email-shape check was added** because the backend's generic Bean Validation messages are emitted in the JVM's default locale, which is not guaranteed to be English (see Known issues). Catching an obviously malformed address locally keeps the ADMIN in the product's own English wording; every backend-specific business message (duplicate email, invalid route assignment, self-protection, duplicate route code, route in use) is already English and is surfaced verbatim.
- **Route-mutation invalidation intentionally spans both resources.** Creating or editing a route invalidates the `['admin','routes']` *and* `['admin','users']` prefixes: every user's nested `route` summary embeds the route's code/name/active state, and the Returns page's driver/route filter dropdowns read the very same two endpoints, so a narrower per-page key would leave both stale. One shared `useAdminRoutes()` also means a newly created route is immediately selectable when assigning a driver, with no second lookup endpoint — covered by a dedicated cross-page integration test.

**Phase 10A — CI/CD readiness (approved):**

- **One workflow per application, with the expensive validation conditionally executed inside each workflow's own stable job.** The combined `ci.yml` had no path filters at all, so a documentation-only commit ran the entire backend suite and the mobile suite. Separate workflows fix that and keep each application's CI independently readable and independently cancellable, while `Backend CI` and `Mobile CI` kept their exact job names through the split precisely because a required-check configuration refers to those names.
- **Pull Requests deliberately carry no workflow-level `paths:` filter; push to `main` still does.** This is the design decision that makes the three checks genuinely requirable. GitHub never reports a check for a workflow that a `paths:` filter prevented from starting, and treats a required-but-unreported check as permanently pending — so filtering at the trigger would deadlock every Pull Request that did not touch that application. A step skipped *inside* a workflow that did start, by contrast, still reports success. So every workflow starts for every Pull Request and decides for itself whether to do real work; required-check reporting is purely a Pull Request concern, so push to `main` keeps an ordinary `paths:` filter and a manual `workflow_dispatch` always validates for real.
- **Relevance is detected with a few lines of `git diff` and `grep`, not a third-party path-filter action.** Each job compares `github.event.pull_request.base.sha` against `.head.sha` — explicitly, rather than diffing the synthetic merge commit, which would also surface changes that arrived from `main` and were never made by the branch — which is why the checkout uses `fetch-depth: 0` so both SHAs are present locally. When nothing relevant changed, the job logs one "validation not required" line and finishes successfully without installing a toolchain. The diff is written to a file and grepped from there rather than piped straight into `grep -q`: these steps run under `pipefail`, and `grep -q` stops reading at its first match, which can leave `git` killed by SIGPIPE and turn a genuine match into a failed pipeline — silently skipping validation that was actually required. The alternative of duplicate no-op jobs sharing a check name was also rejected: a Pull Request touching two applications would then report the same check twice.
- **Root and documentation paths deliberately trigger no application validation.** No root file genuinely participates in any application build — `dev.ps1` and `infra/docker-compose.yml` are local-development only, and the backend's integration tests own their own database through Testcontainers rather than Compose. Treating root paths as relevant "to be safe" would have quietly restored the whole-repo validation this phase set out to remove, while adding nothing.
- **`main` is protected by a repository ruleset requiring `Backend CI`, `Web CI`, and `Mobile CI`.** Requiring all three is only safe because of the decision above — every workflow starts for every Pull Request, so no required check can sit unreported and deadlock a merge. Alongside them: a Pull Request is required, force pushes are blocked, and branch deletion is restricted. Two settings are deliberately relaxed for the current single-developer MVP and should be revisited when that changes — **required approvals are 0** (a second developer makes review meaningful; self-approval does not), and **"require branches to be up to date before merging" is disabled**, trading a small risk of semantic conflict for not re-running every check on every intervening merge. No bypass is intended for the normal workflow.
- **CI deliberately needs no secret of any kind**, and that is treated as a property worth protecting rather than an accident. The backend suite runs against Testcontainers-managed PostgreSQL with the clearly-labelled development-only token secret from `application.properties`; no service container, database credential, or signing key is injected. If a future check appears to need a production credential, that is a signal it is doing deployment work rather than verification.
- **Mobile CI verifies the source, not a signed binary.** No EAS/cloud build, no Android/iOS signing, no store credentials — those depend on pilot-distribution decisions that belong to Phase 10B. Phase 10A's mobile deliverable is that typecheck, lint, and tests run reproducibly on the pinned Node version.
- **One reproducibility detail worth knowing:** `npm run lint` (oxlint) reads its ignore rules from the surrounding Git working tree, so run inside a bare copy of `apps/web` it lints `node_modules` and reports thousands of findings. Inside any real checkout — including `actions/checkout` — it correctly lints 68 source files with zero findings. Recorded in `docs/BUILD_AND_ENVIRONMENT.md` so it is not rediscovered as a phantom lint regression.

**Phase 9 — PDF (approved):**

- **Apache PDFBox 3.0.8, Apache License 2.0** — verified from the artifact's own `META-INF/LICENSE` and `NOTICE` before the dependency was added, not from memory. Apache 2.0 is compatible with commercial SaaS use, which is the whole reason the iText (AGPL/commercial dual) family was excluded by root `CLAUDE.md` §18. Used solely for server-side, on-demand administrative PDF generation. The version is pinned explicitly in `apps/api/pom.xml` because the Spring Boot parent does not manage it. No HTML-to-PDF engine, headless browser, PDF SaaS, or template engine was introduced.
- **Generated on demand and never stored.** Requesting a PDF is a read, not a lifecycle event: nothing is written to PostgreSQL, `ReturnMediaStorage`, MinIO, or the filesystem, no migration was needed or added, and Close still does not generate anything. Two generations of the same record may differ in PDFBox's own document ID/metadata, but the business content is always re-derived from the same authoritative row.
- **Both signatures are redrawn as vector strokes rather than rasterized, and no SVG dependency was added.** PDFBox cannot render SVG, and pulling in Batik (plus its XML stack) to redraw a handful of polylines would have been a large dependency for a tiny need. `SignatureSvgPaths` instead recovers the stroke geometry from the signature SVG *this application generated itself* — `SvgSignatureRenderer` writes one fixed shape (`<path d="M x y L x y ..."/>` over a 1000 x 300 viewBox) from already-validated normalized points — and normalizes it back to 0..1 so the renderer can place it in any box. This is explicitly **not** a general SVG parser and must never be pointed at untrusted markup: it is safe only because the input is never client-supplied, and it interprets nothing but numbers (no entities, external references, scripts, or nested elements). Coordinates are clamped so a stroke can never escape its reserved box, and anything unparseable is skipped rather than thrown, so one odd coordinate cannot fail a whole document.
- **The `pdf` module depends on nothing in `returnrecord`.** `ReturnPdfDocument` carries presentation-neutral primitives (resolved labels, plain `Instant`s, raw signature bytes) rather than domain enums or the entity, so the dependency runs one way — the return domain asks the renderer to draw, never the reverse. This is why `ReturnReasonLabels` lives in `returnrecord`: the labels are a product decision belonging to the domain (root `CLAUDE.md` §10), and its exhaustive `switch` with no `default` turns "added a reason without a label" into a compile error instead of a PDF printing a raw enum code.
- **Free text is sanitized before it is drawn, not trusted to be renderable.** The standard PDF fonts use WinAnsi encoding, and a character outside it makes PDFBox throw — which would turn one unusual customer or product name into a failed download. Common typographic characters (smart quotes, dashes, ellipsis) are transliterated to their ASCII equivalents so they survive meaningfully, and anything still unrepresentable degrades to `?`. Combined with per-value wrapping, per-word character splitting for unbroken strings, and a cursor that starts a new page before crossing the bottom margin, a maximum-length record paginates cleanly instead of overflowing.
- **Print PDF opens the authenticated bytes in the browser's own PDF viewer — no custom print UI, no embedded viewer, no iframe, and no new dependency.** It reuses the same authenticated endpoint and the same fetch-as-`Blob` path as Download; only what happens to the bytes differs. `window.print()` is deliberately **not** called: for a PDF rendered by a native viewer it fires before the document is ready often enough to be unreliable, and the viewer already offers Print, so the requirement is met by simply opening the tab.
- **The print object URL cannot be revoked immediately, so it is released on a bounded 60-second timer — an explicit, documented trade-off.** The new tab has not loaded the URL when `window.open` returns, and revoking first leaves it showing a failed document; there is also no reliable cross-document signal to revoke on, because a native PDF viewer gives the opener no usable `load` event. The blob therefore stays in memory for at most 60 seconds after the tab opens (the tab keeps its own copy once loaded, so printing still works afterwards). It is never a permanent object URL, and Download keeps its original immediate-revoke-in-`finally` behavior unchanged. A blocked pop-up — the one failure the fetch itself cannot report — releases the unusable URL at once and is surfaced as an inline message rather than looking like a no-op.
- **Download and Print each get their own mutation instance**, so one being in flight disables only its own button; the shared `useReturnPdf` hook (renamed from `useDownloadReturnPdf` now that it serves both) still caches and invalidates nothing.
- **The generator formats timestamps in the same configurable business timezone the rest of the backend uses** (`app.operations.business-timezone`), injected directly rather than routed through `OperationalDayService`, which is package-private to `returnrecord` and exposes only day boundaries. The zone abbreviation is rendered from the timestamp itself (`AEST`/`AEDT`), so the document stays self-describing and correct across daylight saving without any manual offset math. Database storage remains UTC and unchanged.

## Known issues

- **The backend's generic Bean Validation messages are returned in the JVM's default locale, not necessarily English** (observed during Phase 8's contract smoke test: a too-short password came back as `password: tamanho deve ser entre 8 e 2147483647` on a machine whose JVM locale is pt-BR). This is pre-existing and API-wide — it affects every `@Valid` failure across all phases, not anything Phase 8 introduced — and conflicts with root `CLAUDE.md` §5 (the product language is English). Every *feature-specific* `ProblemDetail` (duplicate email, invalid route assignment, self-protection, duplicate route code, route in use) is hardcoded English and unaffected. Phase 8 reduces exposure by validating the common cases client-side first, but the real fix is a backend locale configuration change and belongs in a dedicated, separately-approved task — no backend source was changed for it here.
- **The local dev machine still runs Node `20.18.0` and must be manually upgraded to `20.19.4`** (the project's standardized mobile minimum, see Architectural decisions) — a system-level change outside repository files, still not done, and **no longer merely a warning**: as of Phase 10A's validation, `npm run lint` (`expo lint`) in `apps/mobile` now refuses to run at all, exiting with "Node.js (v20.18.0) is outdated and unsupported ... required: >=20.19.4". Mobile lint therefore cannot be verified locally on this machine until Node is upgraded; `tsc` and `jest` still run fine (typecheck clean, 152/152 tests). `Mobile CI` resolves `20.19.4` from `apps/mobile/.nvmrc`, so CI is unaffected and remains the authority for that step. Upgrading local Node is the fix — no repository change is needed.
- **The mobile Jest suite is timing-sensitive on a cold, contended run.** During Phase 10A's clean-install validation the first `npm test -- --ci --runInBand` after a fresh `npm ci` reported 1 failure of 152 while competing with other work (71s total); an immediate re-run passed 152/152 in 13s with no code change. This is the same first-render initialization cost `--runInBand` already exists to contain (see the comment in `mobile.yml`), not a product or test-logic defect. Worth watching on GitHub's 2-core runners; if it recurs there, raise Jest's default timeout for the affected suites rather than weakening the assertions.
- A physical-iPhone walkthrough via Expo Go has still not been performed — the developer's installed Expo Go app version is incompatible with this project's Expo SDK 57, a device/app-store versioning gap unrelated to any code in this repository. Needs an Expo Go update on the test device, not a code change.
- `apps/web`'s pinned toolchain versions (see Architectural decisions) exist for the same underlying Node-version gap; revisit once the local/CI Node baseline moves to `>=20.19`.
- `npm audit` on `apps/mobile` reports moderate/high advisories (`uuid`, `brace-expansion`) — transitive dependencies of Expo's/Jest's own tooling, not fixable without forcing breaking downgrades.
- `expo-doctor` reports 17/18 checks passing (run manually and locally — it is not part of `Mobile CI`, see Architectural decisions); the one failure is a pre-existing dependency-version drift predating Phase 4 (`@types/jest` one major ahead of what Expo SDK 57 expects, plus `expo`/`react-native`/`eslint-config-expo`/`jest-expo` one patch behind the SDK's exact expected pin). `npx expo install --fix` cannot resolve it automatically — it hits an npm `ERESOLVE` peer-dependency conflict on `@react-native/jest-preset` — so this is not a one-command fix and was deliberately not forced with `--legacy-peer-deps`/`--force`. Resolve it in a dedicated, reviewed dependency-maintenance task; Expo Doctor returns to `Mobile CI` as a blocking step only once that task safely reaches 18/18.
- **Bootstrap-only double session-clear race (found in Phase 4 final review):** if a stored refresh token is invalid/revoked at app startup, `apiClient`'s `onSessionExpired` handler and `AuthContext`'s own bootstrap failure path can both independently clear the session, racing to set `sessionMessage` to either "Your session has expired…" or no message. Both outcomes land safely on Login with no session security impact — this is a message-text nondeterminism only. Safe to defer.
- **Theoretical logout-during-refresh token staleness (found in Phase 4 final review):** logging out at the exact instant a background token refresh is in flight could send the best-effort `POST /auth/logout` call with an already-superseded refresh token. Low impact (errors are swallowed, local tokens are always cleared regardless) and safe to defer.
- **Filesystem photo storage requires a persistent volume in any deployed environment (Phase 5A):** `storage.FilesystemReturnMediaStorage` writes under `app.storage.return-media.root`; a typical container filesystem is ephemeral, so without a mounted persistent volume at that path, every uploaded photo is lost on the next deploy or restart. Not an issue for local development. Tracked as a pre-existing, known limitation of the chosen MVP adapter, not a defect — see Architectural decisions.
- **Secure remote photo thumbnails were deferred, not implemented, in Phase 5A:** Return Details and My Returns show only safe photo metadata (position, count) rather than rendering the actual images remotely, because doing so safely (without a token in a URL query string) would need either a custom authenticated-image-loading component on native or a fetch-then-blob-URL approach on web — judged to meaningfully expand this phase's scope. Local thumbnails (already-selected, not-yet-uploaded photos) do render on `AddReturnPhotosScreen`. Revisit if a future phase needs it.
- **Remote authenticated rendering of the captured signature image was deferred, not implemented, in Phase 5B**, for the same reason as photo thumbnails above — Return Details shows only safe metadata (signer name, timestamp, captured/pending state). This remains an approved MVP boundary, not an oversight. Revisit if a future phase needs it.
- **The browser Back button does not trigger the unsaved-review-form confirmation (Phase 7B, deliberate narrow MVP limitation, not an oversight):** `beforeunload` (refresh/tab-close), Return Details' own "Back to Returns" link, and every `AppShell` nav link (Dashboard/Returns/Users/Routes) all correctly confirm before discarding unsaved warehouse-review values — only the browser's native Back/Forward button does not, because `apps/web` uses a plain `<BrowserRouter>` rather than a data router, and React Router's `useBlocker`/`unstable_usePrompt` (the only clean way to intercept Back) require one. The alternative — pushing/popping synthetic `history` entries to trap `popstate` — was deliberately not built: it is brittle (breaks across repeated Back/Forward, can desync from React Router's own history listening) and was explicitly out of this phase's scope. Using Back while the form is dirty silently discards it, exactly as it always would have without any guard at all — a real but narrow gap, not a regression, and safe by construction (nothing was ever transmitted to lose, since there is still no draft persistence anywhere). Revisit only if a future phase migrates to `createBrowserRouter`/`RouterProvider` for other reasons.
- **`react-router-dom@7.18.2` carries an unfixed `npm audit` advisory (GHSA-qwww-vcr4-c8h2)** whose only "fix" is a forced downgrade below 7.12 — not applied, per root `CLAUDE.md` §39.7a. The advisory is scoped to React Router's RSC/"framework mode" (server-rendered data loaders and actions), which this SPA never uses (`BrowserRouter`, no loaders/actions, no server rendering) — see Architectural decisions. Revisit when an upstream patched release exists.
- **Closing the browser tab/session ends an ADMIN's session (Phase 6B1, approved MVP behavior):** because the refresh token lives only in `sessionStorage` and the access token only in memory, there is no "remember me" or persistent-login option in this phase — an ADMIN must sign in again after closing the tab. This is intentional (see Architectural decisions), not an oversight; revisit only if a future phase explicitly decides to trade this safety property for convenience.
- **Local development data (6 returns, one page) was insufficient to exercise Pagination's Next/Previous controls against the real backend** — reported honestly rather than fabricated. Multi-page pagination behavior (page-field reads, Next/Previous, page-reset-on-filter-change) is covered instead by `ReturnsListPage.test.tsx` against mocked multi-page `PageResponse` data. Revisit with real local data once the pilot generates enough returns, or seed a minimal, reversible local dataset in a dedicated task if this needs earlier real-backend verification.
